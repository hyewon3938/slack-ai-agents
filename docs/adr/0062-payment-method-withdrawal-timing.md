# 0062. 결제수단별 출금 시점 구분 — 자금 기준일 도입

- Status: Accepted
- Date: 2026-07-31
- Related: #615
- Refines: ADR 0051 (supersede 아님 — depletion 정의를 결제수단 단위로 세분)
- Tags: data, budget

## Context

ADR 0051은 reservation(미래 의무를 자유 예산에서 예약)과 depletion(실제 결제 시 자금 차감)을 분리하고, depletion을 **결제주기 종료 정산 1곳**으로 일원화했다. 그 주기의 `billing_month` 결제분 전체를 자금에서 한 번에 차감한다.

이 설계는 **모든 결제수단이 후불(신용카드)** 이라는 전제 위에 서 있다. 카드 결제는 사용 시점에 통장 잔액이 줄지 않으므로 "주기 종료에 한꺼번에 빠져나간다"는 근사가 성립한다.

하지만 실제로는 즉시 출금되는 결제수단(현금·계좌이체)과 즉시 입금되는 수입이 함께 쓰인다. 이들은 **기록 시점에 이미 통장 잔액에 반영**돼 있다.

ADR 0051은 이 간극을 자금의 입력 의미로 흡수하려 했다:

> 자금의 입력 의미 = 현금 유동자금 (= 통장 잔액 − 지난 결제 대금)

즉 사용자가 매 결제주기 경계에서 손으로 보정하는 것을 전제했다. 이 전제는 두 가지로 깨진다.

1. **경계에서만 갱신하지 않는다.** 사용자는 주기 도중에도 잔액을 갱신한다. 그 시점의 통장 잔액에는 이번 주기 즉시 출금분이 이미 빠져 있는데, 예산 계산은 그 지출을 자유지출·묶인 돈으로 **다시** 차감한다. 같은 지출이 두 번 반영된다.
2. **결과가 입력 시점에 의존한다.** 주기 초에 입력한 잔액과 주기 말에 입력한 잔액은 같은 재정 상태를 나타내는데도 서로 다른 하루 예산을 만든다. 자금은 예산 계산의 유일한 입력값이므로, 이 흔들림이 곧 하루 예산의 오차가 된다.

수입에는 같은 문제가 **반대 방향으로** 존재한다. 월 배분기(`allocateMonthlyBudgets`)는 이번 주기 수입이 자금에 이미 반영돼 있다고 전제하고 배분만 조정하는데(총액 중립), 정산은 같은 수입을 자금에 한 번 더 더한다.

근본 원인은 **"결제수단마다 통장에서 돈이 빠져나가는 시점이 다르다"는 사실을 시스템이 모른다**는 것이다. 지출이 어느 주기의 예산에 속하는지(`billing_month`)는 정확한데 — 결제주기 경계가 곧 예산 주기 경계이므로 현금도 같은 규칙으로 귀속되는 게 맞다 — 그 돈이 **언제 통장에서 나갔는지**를 구분하지 않는다.

## Decision

결제수단에 **출금 시점(withdrawal timing)** 속성을 도입하고, 자금 값에 **기준일(as-of date)** 을 붙인다. 예산 계산은 입력 잔액에서 주기 시작 기준선을 복원하고, 정산은 아직 반영되지 않은 몫만 적용한다.

### 1. 결제수단 = 출금 시점 속성을 가진 값

결제수단 정의를 한곳(`payment-methods.ts`)으로 모으고 각 수단에 `timing`을 부여한다.

- `immediate` — 기록 시점에 이미 통장에서 나감 (현금·계좌이체)
- `deferred` — 결제주기 종료 후 카드사에 결제됨 (신용카드)

기존 `CARD_BILLING_CYCLES`(카드별 `startDay`)는 이 정의에서 파생시킨다. **`billing_month` 산출 규칙은 바꾸지 않는다** — 미등록 수단이 기본 주기 경계로 떨어지는 현행 동작이 예산 주기와 일치하므로 그대로가 맞다.

미등록 수단의 기본값은 `deferred`. "이미 나갔다"는 주장이 틀리면 자금이 과대 계상되므로, 확신 없는 쪽은 "아직 안 나갔다"로 둔다.

### 2. 자금 = 기준일이 붙은 통장 잔액

`assets`에 `balance_as_of DATE`를 추가한다. 의미는 **"이 잔액은 며칠까지의 입출금이 반영된 값인가"**.

- 사용자 입력 시: 잔액 + 기준일(기본 오늘). 입력값은 **통장 잔액 그대로** — 손으로 보정하지 않는다
- 정산 시: 기준일을 그 주기 종료일로 갱신
- `NULL`인 경우: 주기 시작 이전으로 간주 (복원 0 — 보수적 기본값)

이로써 ADR 0051의 자금 정의 "통장 잔액 − 지난 결제 대금"은 **"기준일 시점의 통장 잔액"** 으로 단순해진다.

### 3. 예산 기준선 복원

예산 계산이 쓰는 자금은 저장값이 아니라 **복원된 기준선**이다.

```
기준선 = 저장된 잔액 + R

R = Σ 이번 주기 지출 중
      · 출금 시점이 immediate 이고
      · date <= 기준일 이고
      · 예산이 별도로 차감하는 항목
```

세 번째 조건이 핵심이다. 복원 대상은 "이미 통장에서 나갔는데 예산이 **또** 뺄 항목"뿐이다. 예산이 애초에 세지 않는 지출(`exclude_from_budget=true`인 일반 지출)은 복원하지 않는다 — 복원하면 없는 돈이 예산에 생긴다.

고정비 자동 기록분(`source='fixed'`)과 할부 회차는 `exclude_from_budget=true`지만 묶인 돈으로 계상되므로 복원 대상이다.

수입은 복원식에 넣지 않는다. 월 배분기가 이미 "수입은 자금에 반영돼 있다"를 전제로 동작하므로 그 전제를 그대로 살린다.

### 4. 정산은 아직 반영되지 않은 몫만

```
자금 차감액 = 그 주기 결제분 전체 − (immediate 이고 date <= 기준일인 지출)
자금 증액   = 그 주기 수입 전체   − (date <= 기준일인 수입)
```

차감액 쪽 복원분은 §3의 `R`과 다르다. 여기서는 **예산 계상 여부와 무관하게** 실제로 통장에서 나간 전액이 대상이다. 정산은 회계이고, §3은 예산이기 때문이다.

정산 후 기준일을 주기 종료일로 옮기면 다음 주기의 복원분은 0에서 시작한다.

### 5. 고정비에 결제수단 부여

`fixed_costs.payment_method`를 추가한다. 자동 기록(`ensureFixedCostExpenses`)이 특정 카드를 하드코딩하던 것을 이 값으로 대체한다.

이 결정이 없으면 §1\~§4가 매 주기 무력화된다. 실제로 현금으로 나가는 고정비가 매번 카드로 기록되고, 사용자가 그때마다 손으로 고쳐야 복원이 성립한다.

### 6. 잠금 검사는 값 변경 시에만

`source='fixed'` 지출의 `exclude_from_budget` 잠금을 **키 존재**가 아니라 **값 변경** 기준으로 판정한다. 현행 구현은 수정 요청에 그 키가 담겨 있기만 하면 막으므로, 금액만 고치는 저장까지 실패한다 — 코드 주석이 밝힌 의도("다른 필드는 자유 수정 가능")와 실제 동작이 어긋나 있었다.

## Alternatives considered

### A. (선택) 기준일 + 기준선 복원

- 장점: 예산 산식·배분기·`billing_month` 규칙 전부 무변경. 삽입점이 자금 읽기 한 곳(`computeTotalAvailable`)과 정산 한 곳으로 좁다. 입력 시점 독립성이 구조적으로 보장된다. 지출을 뒤늦게 기록하거나 금액을 고쳐도 복원이 라이브로 따라간다. 과거 데이터 소급 불필요
- 단점: "저장된 잔액 ≠ 예산이 쓰는 자금"이라는 이중성이 생겨 화면에서 관계를 보여줘야 한다. 개념(기준일)이 하나 늘어난다

### B. 즉시 출금 지출을 기록 시점에 자금에서 바로 차감

사용자가 처음 떠올린 안이고 회계적으로는 가장 자연스럽다.

- 장점: 자금이 통장 잔액의 실시간 추정치가 된다. 개념 추가 없음
- 단점: **예산 표시 모델과 충돌한다.** 화면은 "자유 예산 총액 − 쓴 만큼 = 남은 예산"으로 보여주는데, 자금에서 이미 뺀 지출을 자유지출로 또 빼면 같은 이중 차감이 재현된다. 이를 피하려면 자유지출 집계에서 현금을 제외해야 하고, 그러면 "이번 달 얼마 썼나"가 결제수단에 따라 달라진다
- 기각: 이중 차감의 발생 지점을 옮길 뿐 없애지 못한다. 예산 층은 결제수단을 구분하지 않는 게 옳다

### C. 자금 입력 시점에 복원값을 계산해 확정 저장

- 장점: 기준일 컬럼 불필요. 정산 무변경
- 단점: 저장 후 그 주기의 과거 지출을 추가·수정하면 기준선이 따라가지 않는다. 사용자가 "잔액을 다시 입력하면 고쳐진다"를 알아야 하는 암묵 규칙이 생긴다
- 기각: 정확성이 사용자의 재입력 습관에 의존한다. 애초에 그 습관 위에 얹은 전제가 깨져서 생긴 문제다

### D. 카드 실제 결제일까지 모델링

- 장점: 통장 잔액을 완전히 재현할 수 있다. 주기 종료와 카드 출금 사이의 어긋남도 사라진다
- 단점: 카드별 결제일 마스터가 필요하고, 결제일 변경·영업일 보정 등 카드사 규칙을 따라가야 한다
- 기각(이번 범위): 기준일이 있으면 이 어긋남은 다음 잔액 입력에서 자동 흡수된다. 비용 대비 이득이 낮다

### E. 사용자가 계속 손으로 보정 (현행 유지)

- 기각: ADR 0051이 이미 택했고 깨진 안이다. 보정 습관 자체가 이중 차감을 만드는 역설이 있어, 성실하게 갱신할수록 숫자가 더 틀어진다

## Consequences

### 장점

- 자금 입력 규칙이 **"통장 잔액 그대로"** 한 줄로 줄어든다. 뺄 것을 사용자가 계산하지 않는다
- 하루 예산이 잔액을 언제 입력했는지에 의존하지 않는다
- 예산 층(자유지출 집계)은 결제수단을 구분하지 않는 현행을 유지한다 — 자금 층에만 구분이 생긴다. 두 층의 책임이 분리된다
- 수입의 대칭 이중 계상도 같은 규칙 하나로 함께 해소된다
- 고정비 결제수단이 정의에 들어가므로 매 주기 수기 교정이 사라진다

### 단점 / 제약

- 저장된 잔액과 예산이 쓰는 기준선이 다르다. 자금 화면에서 관계를 보여주지 않으면 "내가 넣은 숫자와 다르다"는 혼란이 생긴다
- 기준일이 오래되면 복원분이 커져 오차 여지도 커진다. 잔액 갱신을 유도하는 표시가 필요하다
- 묶인 돈의 고정비는 `fixed_costs.amount`(계획값) 기준인데 복원은 실제 지출액 기준이다. 변동 고정비에서 둘이 어긋나면 그 차이만큼 예산이 보수적으로 잡힌다 (안전한 방향이라 이번 범위에서는 허용)
- 미등록 결제수단은 `deferred`로 떨어진다. 새 즉시 출금 수단을 쓰기 시작하면 정의에 추가해야 한다
- 과거 주기는 소급하지 않는다. 이미 저장된 정산 스냅샷의 이월값은 실제 자금과 어긋난 채로 남는다

### 후속 작업

- [ ] 기준일 경과 알림 (잔액 갱신 유도)
- [ ] 변동 고정비의 계획값 대 실제값 반영 방식 정리 (`is_variable` 컬럼 활용 여부 포함)
- [ ] 정산 스냅샷 이월 체인과 실제 자금의 기준선 1회 정렬
- [ ] 카드 실제 결제일 모델링 필요성 재검토 (기준일 운영 \~2\~3주기 관찰 후)
