# 0016. LLM 자율 슬롯 + Outcome-based 검증 — 결정론적 SQL 엔진과의 역할 분리

- Status: Superseded by [ADR-0043](0043-retire-v2-llm-autonomous-discovery.md) (#477로 v2 자율 발견 은퇴, 2026-06-07)
- Date: 2026-05-16
- Related: #390 (Phase 2), #393 (마스터), #354 (이 ADR로 supersede)
- Tags: data, insight, llm, process

## Context

Phase 1 (ADR-0014)에서 11개 SQL 패턴 + 임계치 외부화 + 주간 리포트 재구성으로 **결정론적 잔소리 엔진**이 정착됐다. 다만:

- SQL은 명시적 임계치·단일 도메인 한정 — cross-domain 발견(예: "수면 줄어든 시기 ↔ 일정 카테고리 편향" 동조)은 잡지 못함
- 별도 이슈 #354 (LLM 자율 트렌드 인사이트)는 거의 같은 컨셉으로 후순위 보류 중 — 분리 유지보다 통합이 자연스러움
- v2 핵심 철학 두 줄: **LLM 텍스트 해석 의존도 최소화** + **가설 제기 → DB 보존 → 사후 검증**
- 1인 환경에서 Slack reaction(👍/👎) 기반 피드백은 시그널 약함 — 자동 후행 검증으로 정확도 측정 필요
- LLM 자율 분석을 운영하려면 **할루시네이션 완화 + 정확도 측정 사이클** 동시 확보 필수

이 시점에 Phase 2 = "LLM 자율 슬롯 + 측정"을 출범시킨다. 단순한 LLM 호출이 아니라 **가설-검증 파이프라인**으로 설계해야 v2 철학과 정합.

## Decision

네 가지 결정을 한 묶음으로 채택한다.

### 1. LLM 자율 슬롯 신설 — 월요일 09:30 (주간) + 매월 1일 09:30 (월간)

- 주간 리포트(월 09:00, SQL 패턴 결정론적) **직후** 별도 슬롯
- 동선은 가깝지만 카드/메시지 분리 — SQL 결정론과 LLM 자율의 시각적 구분 유지
- 0건 발견 시 메시지 스킵 (no-news is good)
- #354 흡수: 주간 슬롯이 정착되면 월간 슬롯도 같은 구조 재사용

### 2. LLM 컨텍스트 도메인 — `schedule + sleep + routine + expense` 4개

- schedule: 카테고리/상태/시기만 (**제목 텍스트는 LLM에 노출 안 함** — v2 원칙)
- sleep: 시각/길이/중간기상
- routine: template/records 달성률
- expense: 카테고리 빈도/시기만 (**금액은 LLM에 노출 안 함** — 보안 원칙)
- **diary 제외**: 텍스트 해석 의존도 ↑ 위험. Phase 3·4 사주-일기 연동 시스템과 영역 중복
- **saju 제외**: Phase 3·4의 결정론적 매핑 영역과 LLM 자율 영역의 의도 충돌

### 3. Outcome-based 검증 — LLM이 시그널·가설·검증 SQL을 같이 출력

LLM 출력 1개당 다음 구조:

```typescript
interface LlmInsight {
  signal_text: string;          // 현재 관측치 (예: "지난 28일 수면 평균 6.2h")
  hypothesis_text: string;      // 가설 (예: "다음 7일 spotty 패턴 빈도 ↑")
  verification_sql: string;     // LLM이 작성한 검증 쿼리
  verification_result_type:     // 결과 형식
    | 'boolean' | 'scalar_count' | 'ratio';
  verify_at: Date;              // 가설별 가변 (LLM이 자율 결정, 권장 1~4주)
  confidence: 'high' | 'medium'; // 임계치 미만(low)은 발송 자체 안 함
}
```

**안전장치 4종 (검증 SQL 할루시네이션 완화)**:
- SELECT만 허용 (`query_db` 도구 자체가 강제)
- get_schema 선호출 권장 (시스템 프롬프트로 가이드)
- 결과 형식 제약 — boolean / scalar count / 비율값 중 하나만
- 검증 SQL을 `llm_insights`에 영속 — 추후 사람이 검증 로직 점검 가능

**자동 후행 검증 cron**: 매일 1회 `verify_at <= now() AND outcome = 'pending'` 인 row를 verify. 결과 = `hit | miss | inconclusive`.

### 4. 결과 노출 — 점진적, 누적 검증 10건 도달부터

- 초기 4\~6주는 데이터 쌓는 기간 (Slack 정기 노출 안 함)
- 누적 `outcome IN ('hit','miss')` 10건 도달 후, 다음 주 슬롯 첫 줄에 자동으로 "지난주 발견 N개 중 X개 hit" 한 줄 추가
- 임계 미달 동안에도 사용자가 자연어("발견 검증 어땠어", "정확도" 등) 입력 시 fast path로 즉시 조회

## Alternatives considered

### A. Reaction 기반 피드백 (👍/👎)

- 장점: 구현 단순, 자연스러운 사용자 입력
- 단점: 1인 환경에서 시그널 매우 약함 — "무시 = 무관심인지 잘못된 발견인지 구분 불가". 통계적 의미 확보까지 수개월 소요
- 기각 이유: v2 철학("사후 검증") 미충족. 정확도 측정 사이클이 안 돌아감

### B. 카탈로그 기반 검증 — 11개 detect 함수 중 LLM이 고름

- 장점: 안전. 할루시네이션 구조적 차단
- 단점: LLM 발견 폭이 11개 SQL 패턴 안으로 제약됨. cross-domain 자유 표현 불가능
- 기각 이유: Phase 2의 본래 목적(SQL이 못 잡는 발견 위임)과 충돌

### C. diary / saju 컨텍스트 포함

- 장점: 풍부한 시그널, 감정-패턴 cross 발견 가능
- 단점:
  - diary: 사용자 텍스트 원문 LLM 노출 — v2 핵심 철학 위배 + 프라이버시
  - saju: Phase 3·4의 결정론적 매핑 영역을 LLM 자율 침범 → 의도 충돌
- 기각 이유: v2 단계별 역할 분리 원칙 위반. 정성 해석은 Phase 3/4 사주 가설-검증으로 분리되어 있음

### D. 본 결정 — LLM 자율 슬롯 + 4도메인 + outcome 검증 + 점진적 노출 (선택)

- 장점: 가설-검증 사이클로 LLM 신뢰도 자동 측정. 1인 환경 적합. Phase 3·4 영역과 깔끔히 분리. #354 supersede 가능.
- 단점: 검증 SQL 할루시네이션 잔존 위험 (안전장치 4종으로 완화). 데이터 누적 4\~6주 필요해 초기 효과 검증 느림.

## Consequences

### 장점

- **가설-검증 사이클로 자동 측정**: 1인 환경에서도 정확도 수치화 가능
- **v2 철학 정합**: 매일 잔소리(SQL, 결정론) ↔ 주/월 발견(LLM, 자율) 역할 분리 명확
- **#354 supersede**: 동일 컨셉 이슈 정리, 마스터 #393 phase 흐름 단순화
- **확장성**: 누적 데이터가 4\~6주 쌓이면 검증 SQL 패턴이 카탈로그화 가능 (Phase 2.5 후속)
- **점진적 노출**: 초기 노이즈 회피, 임계 미달 동안엔 fast path만으로도 조회 가능

### 단점 / 제약

- **검증 SQL 할루시네이션 잔존**: 안전장치 4종으로 완화하지만 100% 차단은 어려움. 검증 SQL 자체가 잘못된 경우(존재 안 하는 컬럼/잘못된 집계) outcome 신뢰도 오염
- **초기 운영 4\~6주는 슬랙 노출 없음**: 사용자가 직접 fast path 호출 안 하면 발견 자체를 모를 수 있음
- **운영 비용**: 주간 + 월간 LLM 호출 + 매일 검증 cron 추가 (검증 SQL은 결정론적 SELECT이므로 비용 미미하지만 LLM 호출 비용은 추가)
- **신규 테이블 1개 + 마이그레이션**: 운영 DB 적용 필요

### 후속 작업

- [ ] llm_insights 테이블 정확도 조회 SQL 정착 (fast path용)
- [ ] 누적 검증 10건 도달 시 자동 노출 트리거 확인 (1\~2개월 운영 후)
- [ ] 검증 SQL 카탈로그 진화 가능성 검토 — 자주 쓰이는 검증 패턴 발견 시 헬퍼 함수화
- [ ] 월간 슬롯 시각 미세 조정 (월 1일 09:30이 적정한지 운영 후 판단)
- [ ] #354 close (이 ADR이 superseded 명시)
- [ ] 1\~2주 운영 후 LLM 발견 빈도/품질 관찰 → 컨텍스트 도메인 가감 검토 (특히 expense 카테고리/시기만 노출이 충분한 신호인지)
