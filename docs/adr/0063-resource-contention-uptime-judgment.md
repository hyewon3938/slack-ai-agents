# 0063. 자원 경합 구간의 업타임 판정 — 리소스 경계 + 저하 사후 기록

- Status: Accepted
- Date: 2026-08-19
- Related: #621, [ADR-0055](0055-uptime-deadman-heartbeat.md)
- Tags: infra, observability, reliability

## Context

[ADR-0055](0055-uptime-deadman-heartbeat.md)는 후속 작업으로 "한 달 운영 후 dead-man 오탐 빈도 점검, grace 튜닝 필요 시 재평가"를 남겨두었다. 도입 6주 후 첫 오탐 표본이 확보되어 그 재평가를 수행한다.

### 관측된 실패 모드

단일 호스트를 공유하는 워크로드 사이에 메모리 경합이 발생하자 다음이 동시에 성립했다.

- 봇 컨테이너는 살아 있음 — `RestartCount=0`, 컨테이너 healthcheck 통과
- 호스트 내부 헬스 엔드포인트는 정상 응답 (200)
- 그러나 외부 관측은 타임아웃 후 503으로 판정 → 다운 알림 발생
- heartbeat의 외부 ping 송신 자체도 타임아웃으로 실패 → dead-man's-switch가 "핑 부재"로 알림

경합이 해소되자 아무 조치 없이 정상으로 복귀했다. 즉 **봇 장애가 아니라 오탐**이었다.

### 문제의 본질

현재 구조에서 heartbeat가 만들어내는 신호는 두 가지뿐이다.

| 신호 | 의미 |
|------|------|
| base URL로 ping 도착 | 정상 |
| `/fail`로 ping 도착 | 봇이 스스로 이상을 인지 |
| **ping 부재** | **죽음 · 느려짐 · 네트워크 단절이 모두 여기로 수렴** |

"느려짐"을 표현할 자리가 없다. 그리고 압력이 심할수록 봇은 자기 상태를 보고할 능력을 함께 잃기 때문에, 저하가 심할수록 신호는 죽음과 구분 불가능해진다.

### 자동 복구가 동작하지 않는 이유

세 층이 모두 이 실패 모드를 커버하지 못한다.

1. Docker `restart: unless-stopped`는 프로세스 **종료** 시에만 재시작한다. 프로세스가 살아서 느려지기만 하면 트리거되지 않는다.
2. 컨테이너에 리소스 경계가 없어 커널이 원인 워크로드를 정리하지 않고, 스왑으로 버티며 전체가 함께 저하된다. OOM 킬 기록이 없다는 것이 이 상태의 증거다.
3. 외부 모니터링은 알림만 하고 조치하지 않는다.

### 반드시 기록해야 할 오해

**"컨테이너에 메모리 상한을 걸면 봇이 보호된다"는 것은 사실이 아니다.** cgroup 상한은 *상한*이지 *예약*이 아니다. 봇에 상한을 걸면 외부 압력으로부터 보호되는 것이 아니라, 봇이 더 빨리 정리 대상이 될 뿐이다. 외부 워크로드가 만드는 압력은 봇 자신의 상한으로 막을 수 없다.

따라서 리소스 경계의 목적은 자기방어가 아니라 **자기 억제**로 정의해야 한다.

### 제약 조건 (ADR-0055에서 계승)

- **비용 0원 유지**
- **모니터는 대상 바깥에서 관측**
- **배포 파이프라인에 편승** — 별도 수동 인프라를 늘리지 않는다
- **점진 도입 안전성**

## Decision

**리소스 경계로 저하의 성질을 바꾸고, heartbeat는 저하를 사후에 기록한다. 저하는 알림을 발생시키지 않는다.**

네 가지를 함께 적용한다. 개별로는 어느 하나도 충분하지 않고, 조합에서만 의미가 성립한다.

### 1. 컨테이너 리소스 경계 (자기 억제)

봇·DB 컨테이너에 상한(`mem_limit`)과 소프트 예약(`mem_reservation`)을 명시한다. 목적은 두 가지다.

- 봇·DB가 경합의 **원인이 되지 않도록** 상한을 못박는다
- 소프트 예약으로 회수 압력에서 최소 작업 집합을 보호한다

### 2. 호스트 스왑 정책 조정

`vm.swappiness`를 낮춰 커널이 익명 메모리를 스왑으로 밀어내기보다 페이지 캐시를 먼저 회수하게 한다. 이로써 실패의 **성질**이 바뀐다.

- 이전: 전원이 스왑 스래싱으로 함께 느려지고, 아무도 죽지 않아 상태가 무한히 지속됨
- 이후: 압력이 임계를 넘으면 커널이 가장 큰 소비자를 정리하고, 나머지는 정상 속도를 유지

### 3. OOM 희생자 우선순위 조정

2번이 OOM 발생 확률을 **의도적으로 높이기** 때문에, 봇·DB에 `oom_score_adj`를 낮춰 정리 대상 우선순위에서 뒤로 뺀다. 2번과 3번은 반드시 함께 가야 한다 — 2번만 적용하면 봇이 희생자가 될 수 있다.

### 4. heartbeat 타임아웃 확대 + 저하 사후 기록

- **타임아웃 확대**: ping 송신 타임아웃을 늘려 압력 구간에서도 송신이 성사되게 한다. ping이 도착하기만 하면 dead-man은 정상으로 판정하므로 **오탐이 사라진다.**
- **저하 사후 기록**: 사이클마다 헬스 판정 소요시간을 누적하고, 회복 후 첫 성공 ping의 body에 저하 이력을 동봉한다. 침묵 구간이 끝난 뒤에라도 "느렸다"와 "죽었다"가 구분된다.
- **알림 없음**: 저하는 기록으로만 남기고 알림을 발생시키지 않는다.

### 설계 포인트

- 저하 판정에 필요한 재료(헬스 소요시간)는 기존 `/health/detail`이 이미 계산하는 값과 동일 의미론이다.
- heartbeat는 여전히 어떤 경우에도 봇을 죽이지 않는다 — 누적 상태는 인메모리, 전송 실패는 로그만.
- 저하 이력이 소실돼도(프로세스 재시작 등) 기능 손실이 아니다. 저하 기록은 진단 보조이지 판정 근거가 아니다.

### ADR-0055 제약과의 긴장 — 명시적 해석

2번(`vm.swappiness`)은 호스트 설정 변경이므로 "별도 수동 인프라를 늘리지 않는다"는 제약과 부딪히는 것처럼 보인다. 다음과 같이 해석을 좁혀 채택한다.

> 해당 제약의 취지는 **상주하며 반복 실행되는 태스크**(호스트 crontab 등)를 배포 파이프라인 밖에 만들지 않는다는 것이다. 1회성 커널 파라미터 튜닝은 상주 태스크가 아니므로 제약의 대상이 아니다.

다만 VM 재프로비저닝 시 재설정 누락 위험은 실재하므로, 운영 문서에 재프로비저닝 체크리스트 항목으로 남긴다.

## Alternatives considered

### A. 호스트 systemd slice로 원인 워크로드에 하드 상한

- 장점: 경합을 가장 확실하게 차단. 원인을 직접 봉쇄하므로 다른 수단에 의존하지 않음
- 단점: 상한에 걸린 워크로드가 실패할 수 있음(메모리를 많이 쓰는 빌드는 상한 자체를 통과 못 할 수 있음). 배포 파이프라인 밖의 지속적 수동 설정이 늘어남
- 기각 이유: **차선이 아니라 순서의 문제.** 더 싼 수단(스왑 정책)으로 실패의 성질이 바뀌는지 먼저 확인해야 한다. 싼 수단이 불충분한 것이 관측되면 승격한다

### B. 능동 폴링 도입 (ADR-0055 Alternative C 복권)

- 장점: 봇이 침묵하는 구간에도 바깥에서 응답 지연을 직접 측정 가능. 저하와 죽음을 **실시간으로** 구분할 수 있는 유일한 안. 실제로 이번 사건에서 2차망 폴링이 봇 자신보다 많은 정보(503, 지연 시간)를 관측했다
- 단점: 외부 서비스 의존 추가, 계정·정책 변동 관리 부담
- 기각 이유: 오탐 표본 1건에 외부 의존을 늘리는 것은 과잉. 사후 기록으로 구분 목적은 달성되고, 실시간 구분이 필요할 만큼 저하가 잦아지면 그때 승격한다. **후속 후보로 유지**

### C. 저하도 알림 (등급 분리 알림)

- 장점: 저하를 즉시 인지하고 대응 가능
- 단점: 이번 사례처럼 저하가 스스로 해소되는 경우가 많으면 알림 무감각을 부른다. 알림 위생이 나빠지면 진짜 다운 알림의 신뢰도까지 함께 떨어진다
- 기각 이유: 기록만으로 시작한다. 저하 이력이 쌓여 대응이 필요한 패턴이 확인되면 그때 알림 승격을 판단

### D. dead-man grace 확대만 (ADR-0055 후속의 최소안)

- 장점: 설정 한 줄. 코드 변경 없음
- 단점: 감지 창을 넓히면 오탐은 줄지만 **진짜 다운의 감지도 같이 늦어진다.** 오탐과 미탐을 맞바꾸는 것에 불과하며, ADR-0055가 감지 창을 좁히려 했던 목적을 되돌린다
- 기각 이유: 문제는 감지 창의 폭이 아니라 신호의 해상도다. grace로는 "느려짐"을 표현할 자리가 생기지 않는다

### E. 현상 유지

- 장점: 작업 없음
- 단점: 호스트를 공유하는 워크로드가 늘어나는 추세라 경합은 재발이 예정되어 있다
- 기각 이유: 오탐이 반복되면 알림 신뢰도가 떨어지고, 진짜 다운을 오탐으로 오인할 위험이 생긴다

### F. 리소스 경계 + 스왑 정책 + OOM 우선순위 + 타임아웃 확대 + 저하 사후 기록 (선택)

- 장점:
  - 오탐의 직접 원인(ping 송신 실패)을 제거
  - 실패의 성질을 "무한 저하"에서 "정리 후 정상"으로 변경
  - 봇이 정리 대상이 될 확률을 낮춤
  - 저하와 죽음이 사후에 구분됨
  - 외부 서비스 추가 없음 → 비용 0원 제약 유지
  - 알림 등급을 늘리지 않음 → 알림 위생 유지
- 단점: 봇이 침묵하는 구간의 **실시간** 구분은 여전히 불가 (대안 B의 영역). 저하 기록은 회복 이후에만 도착한다

## Consequences

### 장점

- 자원 경합으로 인한 다운 오탐이 제거된다
- 경합이 무한히 지속되는 대신 커널이 정리하고 정상 속도로 복귀한다
- 봇·DB가 경합의 원인이 될 수 없도록 상한이 코드로 명시된다
- 저하 이력이 관측 가능해져, 알림 없이도 경합 빈도를 추적할 수 있다
- 비용 0원, 외부 의존 불변

### 단점 / 제약

- **실시간 구분은 여전히 불가** — 봇이 침묵하는 동안의 상태는 회복 후에야 알 수 있다. 완화: 실시간 구분이 필요해지면 대안 B 승격
- **호스트 설정 의존 추가** — VM 재프로비저닝 시 스왑 정책 재설정이 필요하다. 완화: 운영 문서 체크리스트
- **OOM 발생 확률이 의도적으로 상승** — 정리가 일어나는 것이 설계 의도다. 봇이 희생자가 되지 않도록 `oom_score_adj`가 함께 적용되어야 하며, 둘 중 하나만 적용하면 안 된다
- **상한 설정값은 추정** — 현재 사용량 기준으로 여유를 두고 잡았으나, 예상 못 한 스파이크에 봇이 상한에 걸릴 수 있다. 완화: 운영 관찰 후 조정

### 후속 작업

- [ ] 배포 후 리소스 경계가 실제 적용됐는지 확인
- [ ] 다음 경합 발생 시 오탐이 사라졌는지, 저하 이력이 남는지 확인
- [ ] 저하 이력이 누적되면 빈도·지속시간 분포 점검 → 알림 승격(대안 C) 또는 slice(대안 A) 필요성 판단
- [ ] 봇 상한 도달 사례가 관측되면 상한값 재조정
- [ ] 실시간 구분이 필요해지면 능동 폴링(대안 B) 재검토
