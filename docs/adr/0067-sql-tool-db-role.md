# 0067. SQL 도구 전용 DB 역할과 권한 동기화

- Status: Accepted
- Date: 2026-11-25
- Related: #663, #664, ADR-0001, ADR-0066
- Tags: security, data, agent, infra

## Context

봇의 LLM은 `query_db`와 `modify_db` 도구로 SQL을 직접 작성하고(ADR-0001), 코드는 실행 전에 토큰 기반 검사로 그 SQL을 확인한다(ADR-0066). 이 SQL은 크론, 마이그레이션, 웹 대시보드용 프록시와 같은 연결 풀에서 앱 역할로 실행된다.

검사와 별개로 DB가 한 번 더 판단하게 하려면, LLM이 쓴 SQL이 실행되는 연결의 역할부터 앱 역할과 달라야 한다. 그래야 검사 규칙이 바뀌거나 검사가 놓친 쿼리가 있어도 역할에 권한이 없는 작업은 DB가 거절한다.

도구가 다루는 범위도 좁다. 에이전트 프롬프트가 변경 대상으로 안내하는 테이블은 10개이고, 나머지 사용자 데이터는 읽기만 하면 된다. 확인 카드가 실행할 SQL을 담는 `pending_modify`처럼 도구가 읽거나 바꾸면 안 되는 테이블도 있다.

## Decision

LLM이 쓴 SQL은 권한을 줄인 전용 역할로 접속하는 두 번째 연결 풀에서 실행하고, 그 역할의 권한은 코드에 둔 목록 하나로 관리한다.

- 봇 안에 두 번째 풀(크기 2)을 두고 연결 문자열은 `SQL_TOOL_DATABASE_URL`로 받는다. `query_db` 조회, `modify_db`의 미리 실행과 실행, 확인 카드의 실행 버튼이 이 풀을 쓴다. `get_schema`와 `pending_modify` 처리, 고정 쿼리를 쓰는 앱 코드는 기존 풀에 남는다.
- 도구 연결은 쿼리가 끝나면 `RESET statement_timeout`으로 역할 기본값으로 돌아간다.
- 전용 역할은 로그인 외의 관리 속성을 모두 끄고 어떤 역할에도 소속시키지 않는다. 연결 수와 문장·잠금·유휴 트랜잭션 제한 시간을 역할 기본값으로 걸고, DB에는 `CONNECT`, `public` 스키마에는 `USAGE`만 준다. 운영자가 `scripts/create-sql-tool-role.sh`로 한 번 만들고 비밀번호는 `psql`의 `\password`로 입력한다.
- 테이블 권한은 `src/shared/sql-tools/table-permissions.ts`에 둔다. 마이그레이션에 있는 모든 테이블과 뷰를 읽고 쓰기, 읽기만, 권한 없음 가운데 하나로 적고, 읽고 쓰기 테이블은 작업별로, 필요하면 컬럼별로 권한을 적는다.
- 봇은 시작할 때 마이그레이션을 끝낸 뒤 이 목록대로 권한을 맞춘다. 한 트랜잭션 안에서 도구 역할의 `public` 테이블·시퀀스·함수 권한을 모두 거두고 목록대로 다시 준다. 시퀀스 `USAGE`는 `INSERT`를 준 테이블의 것에만 주고, `public` 함수는 `PUBLIC`의 실행 권한을 거둔다. 역할이 없거나 앱 역할과 같거나 넓은 속성을 가졌으면 경고를 남기고 건너뛴다.
- SQL 검사가 변경 대상을 판단할 때도 같은 목록을 읽는다. 검사와 DB 권한이 같은 범위를 허용하므로 검사를 통과한 변경이 권한 오류로 거절되는 경우가 줄어든다.
- 마이그레이션의 테이블이 목록에 모두 있는지, 목록과 SQL 검사의 판단이 같은지, 목록에서 만든 GRANT 문이 맞는지를 DB 없이 정적 테스트로 확인한다.
- 이 단계에서는 도구 쪽 어느 단계가 실패해도 봇은 시작하고, SQL 도구는 기존 풀로 실행된다. `SQL_TOOL_DATABASE_URL`이 없거나, 역할이 없거나, 넓은 속성의 역할을 가리키거나, 동기화 SQL이 실패하거나, 비밀번호가 틀려 연결하지 못하면 경고나 에러 로그를 남긴다. 동기화에 성공했을 때만 도구 풀을 열어서, 동기화를 건너뛴 역할로 풀이 열리지 않게 했다. 운영에서 필수로 바꿔 도구 풀이 없을 때 SQL 도구 실행을 거절하는 일은 #665에서 한다.

## Alternatives considered

### A. 같은 풀에서 `SET ROLE`로 역할 전환

- 장점: 연결 문자열이 하나로 유지되고 비밀번호 관리가 필요 없다.
- 단점: 역할을 바꾼 세션은 원래 역할로 되돌아갈 수 있다.
- 기각 이유: 되돌아가는 SQL을 막는 일이 다시 SQL 검사에 맡겨져, 검사와 DB 권한을 따로 두려는 목적과 맞지 않는다.

### B. 마이그레이션 파일에 GRANT 작성

- 장점: 권한 변경이 스키마 변경과 같은 파일에 남는다.
- 단점: 역할이 없는 DB에서는 마이그레이션이 실패해 봇이 뜨지 못한다. 권한 정보를 빼고 복원한 DB에서는 이미 적용된 파일이라 다시 실행되지 않는다.
- 기각 이유: 복원 뒤 권한을 되돌리는 절차가 따로 필요해지고, 권한 목록이 여러 파일에 흩어진다.

### C. `ALTER DEFAULT PRIVILEGES`로 새 테이블에 자동 부여

- 장점: 새 테이블을 만들 때 권한을 따로 신경 쓰지 않아도 된다.
- 단점: 목록에 넣기 전의 테이블에도 권한이 붙는다.
- 기각 이유: 목록에 적은 테이블에만 권한을 주는 허용 목록 원칙과 반대로 동작한다.

### D. 행 수준 보안(RLS) 함께 도입

- 장점: 사용자별 행 구분을 DB가 맡는다.
- 단점: 사용자 데이터 테이블마다 정책을 두고 새 테이블마다 더해야 한다. 정책이 현재 사용자를 알려면 연결마다 값을 넣어야 하는데, 세션 설정값에 기대는 정책은 SQL 검사와 같은 전제에 놓인다.
- 보류 이유: 사용자가 사실상 1명이라 지금 얻는 것이 적다. 전용 역할이 생겨 정책을 걸 대상이 그 역할 하나로 좁아졌으므로, 사용자가 2명 이상이 될 때 사용자별 DB 역할 방식과 함께 다시 검토한다.

### E. 전용 역할 + 봇 시작 시 권한 동기화 (선택한 안)

- 장점: 권한 목록이 코드 한 곳에 있고, 복원 뒤에도 봇을 다시 시작하면 권한이 맞춰진다. SQL 검사와 DB 권한이 같은 목록을 읽는다.
- 단점: 연결 2개와 환경변수 1개, 운영자가 역할을 만드는 절차 1회가 늘어난다.

## Consequences

### 장점

- 검사를 통과한 SQL이라도 역할에 권한이 없으면 DB가 거절한다. 사용자·연결 매핑, 확인 대기 테이블, 마이그레이션 기록은 도구 연결에서 읽을 수 없다.
- 쓰기 권한은 프롬프트가 안내하는 10개 테이블로 좁혀지고, 그 안에서도 알림 설정은 시각 변경만, 일정 변경 이력은 삭제 사유 컬럼 변경만 허용한다.
- 도구 연결에서 테이블·임시 테이블 생성과 `public` 함수 직접 호출이 막힌다.
- 문장 제한 시간이 역할 기본값으로 걸려 코드가 정리 단계를 빠뜨려도 유지된다.

### 단점 / 제약

- 새 테이블을 만들면 권한 목록에도 넣어야 하고, 넣지 않으면 테스트가 실패한다. 도구가 새 테이블을 바꿔야 하면 목록과 SQL 검사가 같이 바뀐다.
- 트리거 함수는 SQL을 실행한 역할의 권한으로 돌기 때문에, `schedules`를 바꾸면 기록이 남는 `schedule_changes`에 `INSERT`와 시퀀스 `USAGE`를 줘야 한다. 트리거가 다른 테이블에 쓰게 바뀌면 목록도 함께 고친다.
- 백업을 복원하면 권한이 비므로 봇을 다시 시작해야 한다. 절차는 `docs/ops/db-backup.md`와 `docs/ops/sql-tool-role.md`에 있다.
- 실제 DB에 권한을 적용해 거절을 확인하는 검사는 CI에 DB가 없어 로컬 확인으로만 한다.
- 뷰 3개는 만든 역할의 권한으로 기반 테이블을 읽기 때문에 권한을 주지 않았다.
- #665 전까지는 도구 풀을 열지 못해도 봇이 기존 풀로 계속 동작하므로, 운영 전환은 시작 로그의 동기화 완료와 도구 풀 연결 완료 두 줄로 확인한다.
