# 0054. 일정 날짜 변경 신호의 순변위 측정 + 기록 경로 트리거 단일화

- Status: Accepted
- Date: 2026-07-04
- Related: [#572](https://github.com/hyewon3938/slack-ai-agents/issues/572), [#508](https://github.com/hyewon3938/slack-ai-agents/issues/508)(방향 분리 선행), [ADR-0044](0044-discovery-measurement-validity.md)(데이터-존재 윈도우), [ADR-0046](0046-signal-seed-precision.md)(방향 분리 + 측정 정의만 교정 원칙), [ADR-0048](0048-enrollment-clip-and-rebaseline.md)(enrollment 클립·re-baseline 의무)
- Tags: insight, data, statistics, architecture

## Context

#508(ADR-0046)이 일정 날짜 변경 신호를 미룸/당김 방향 2개로 분리했지만, 운영 데이터에서 측정 아티팩트 4종이 추가로 확인됐다.

- **왕복 상쇄 미처리**: 신호가 변경 이벤트 1건 단위로 방향을 판정한다. 하루 안에 일정을 미뤘다가 되돌리면(순변위 0) 미룸·당김 양쪽 모두 발화. prod 정량: 당김 발화일 13일 중 3일(23%)이 왕복 아티팩트. 표본이 작은 당김 신호는 이 오염이 신호 자체를 지배할 수 있는 규모.
- **생성 직후 교정 미구분**: 일정을 만들자마자 날짜 오기입을 고치는 행위가 미룸/당김으로 집계된다. 같은 테이블을 쓰는 구형 신호 `audit_postponed_done`(052)은 `created_at + 30분` 유예를 이미 적용 중인데, #508 신설 방향 신호에는 이 필터가 누락됐다.
- **기록 경로 비대칭**: `schedule_changes` audit은 웹 앱 코드만 기록한다. Slack 카드 버튼(내일로 미루기·오늘로 옮기기)과 에이전트 `modify_db` 경로의 날짜 변경은 기록되지 않아, 신호가 사실상 "웹에서 미룬 날"만 측정한다. 채널 선택이 그날의 상황과 상관되면 랜덤 결측이 아니라 체계적 편향이 된다.
- **이력 소급 소멸 + 윈도우 어긋남**: `schedule_changes.schedule_id`가 `ON DELETE CASCADE`라 일정 삭제 시 변경 이력이 통째로 사라진다 — "미루다 포기하고 지운 일정"이 미룸 데이터의 핵심 케이스인데 그게 증발한다. 또 데이터-존재 윈도우(ADR-0044)의 audit 도메인 매핑이 `schedules` 첫 데이터(2026-03-05) 기준이라, 기록 계기(`schedule_changes`) 도입일(2026-05-18) 이전의 측정 불가능 시기(전체 윈도우의 약 60%)가 "변경 없음" 날로 발굴 2×2에 들어간다.

측정 오염은 통계 하류에서 교정할 수 없고(GIGO, #504 원칙 ①), 랜덤 오분류는 효과를 희석시키는 데 그치지만 체계적 오염은 가짜 패턴을 만든다. #508과 동일하게 **무엇을 측정하는지만 교정하고 통계 스택·verdict·tier·임계치는 불변**으로 둔다.

설계 중 요구가 하나 추가됐다: **생성일 코호트 추적**([#574](https://github.com/hyewon3938/slack-ai-agents/issues/574)) — 특정 조건의 날(예: 특정 십성 강도 발현일)에 생성된 일정이 이후 더 미뤄지거나 결국 삭제되는지 보고 싶다는 것. 가설·검증 레이어는 성숙 기간 설계가 필요해 #574로 분리하지만, **캡처 계층은 소급 불가**(삭제 이벤트는 지나가면 영영 유실)라 본 건에 포함한다. 이 요구가 아래 §4의 메커니즘 선택을 바꿨다.

## Decision

### 1. 순변위(net displacement) 측정 — 방향 분리는 유지

미룸/당김 신호를 이벤트 단위에서 **(일정 × 하루) 그룹 단위**로 재정의한다. 그날 그 일정의 첫 `before_value` 날짜와 마지막 `after_value` 날짜를 비교해 순변위 방향만 센다.

- 미뤘다 되돌린 왕복(순변위 0)은 **미룸·당김 어느 쪽에도 세지 않는다**
- 여러 번 나눠 미뤄도 하루 1회로 정규화 (여러 일정을 미루면 일정 수만큼)
- 날짜를 넘긴 왕복(오늘 미루고 내일 되돌림)은 각 날의 실제 행동이므로 각각 집계 — 신호 의미가 "일정을 미룬 날"이라 하루 경계가 정합

이는 ADR-0046이 기각한 "방향무관 합산"으로의 회귀가 **아니다**. 방향 신호 2개는 그대로 유지하고, 반대 방향 이벤트가 서로 상쇄되는 왕복 쌍만 양쪽에서 제외한다 — 반대 의미 합산 금지 원칙(ADR-0046 §1)을 오히려 강화하는 방향.

`audit_postponed_done`("여러 번 미룬 일정을 완료한 날")의 자격 조건도 raw 변경 횟수(`n >= 2`, 방향 무시)에서 **순미룸 일수 ≥ 2**로 재정의한다. 현행 기준은 왕복 1회(=2행)만으로 자격이 생겨 36개 자격 일정 중 4개(11%)가 부풀려져 있다.

### 2. 생성 30분 유예 통일

세 신호 모두 `changed_at > 생성시각 + 30분` 필터를 적용한다. 30분 이내 변경은 날짜 오기입 교정으로 간주.

- 경계값은 052 전례 재사용 — 새 임의값을 만들지 않음(#434 헌장 ⑤)
- prod 분포 근거: 생성 당일 변경 35건 중 30분 내 3건 / 30분\~2시간 5건 / 2\~6시간 8건 / **6시간 이상 17건**. 당일 전체 유예는 "아침에 만들고 저녁에 미룸"이라는 전형적 진짜 미룸(17건+)을 잃는 과잉
- ADR-0048의 enrollment 클립과는 다른 레이어다: 클립은 **가설(링크) 등록일** 기준으로 검정 시작일을 미는 장치고, 이 유예는 **일정 행 생성** 후 이벤트가 행동인지 교정인지를 판별하는 장치

### 3. 기록 경로 DB 트리거 단일화

`schedules.date` UPDATE 시 PostgreSQL 트리거(`AFTER UPDATE OF date ... WHEN (OLD.date IS DISTINCT FROM NEW.date)`)가 `schedule_changes`에 자동 기록한다. 웹 앱의 수동 기록 코드(`recordScheduleChanges`)는 제거(이중 기록 방지).

- 웹 PATCH · Slack 버튼 · 에이전트 `modify_db` · 수동 psql까지 **모든 경로가 단일 계기로 수렴** — 앱 레벨 확장으로는 LLM 자유 SQL 경로를 구조적으로 커버할 수 없다
- schedules에는 이미 027의 `updated_at` 자동 갱신 트리거 전례가 있다 — 같은 패턴(함수 + `CREATE TRIGGER`)의 두 번째 적용. "코드에서 로직이 안 보인다"는 비용은 도메인 문서·마이그레이션 주석으로 상쇄하고, 기록 로직이 writer 수만큼 복제되는 것보다 계기 1개가 낫다고 판단

### 4. 이력 보존 — audit 로그화(FK 제거) + 생성시각 스냅샷 + 삭제 tombstone

- `schedule_changes.schedule_id`의 FK를 **제거**하고 append-only 로그 테이블로 전환 — 일정을 지워도 변경 이력이 `schedule_id` 그대로 남는다. 무결성은 writer가 트리거뿐이므로 유지
- 인터뷰 초안은 `ON DELETE SET NULL`이었으나 기각(Alternatives G): 삭제 시 그 일정의 **모든** audit 행 `schedule_id`가 일괄 NULL이 되어 (일정×하루) 그룹핑이 붕괴 — 여러 삭제 일정의 이력이 NULL 한 그룹으로 뭉개져 순변위 재계산이 삭제 후 비결정적이 되고(#477 결정론 리플레이 훼손), 코호트 추적(#574)도 불가능해진다
- `schedule_created_at TIMESTAMPTZ` 컬럼 신설, 트리거가 기록 시점에 `schedules.created_at`을 스냅샷 — 30분 유예 판정이 `schedules` JOIN 없이 자립해 삭제 후에도 유효
- **삭제 tombstone**: `AFTER DELETE` 트리거가 `change_type='deleted'` 행 기록(`change_type` CHECK 확장). `before_value`에 삭제 시점의 `{date, status, category_id}`만 담는다 — "미뤄지다 결국 삭제"라는 운명이 처음으로 측정 가능해짐
- 스냅샷·tombstone 모두 날짜·시각·id뿐 — 일정 제목 등 원문은 저장하지 않는다 (v2 헌장 ①)

### 5. 데이터-존재 윈도우 audit 매핑 교정

`DOMAIN_TABLE`의 `audit` 매핑을 `schedules` → `schedule_changes`(첫 기록일 = KST `changed_at` 최소값) 기준으로 바꾼다. 기록 계기가 존재하지 않던 시기는 발굴·검증 모두에서 결측 처리 (ADR-0044 매핑 보완).

### 6. 신호 처분 — 은퇴 + 신설, re-baseline 해당 없음

구 신호 3개는 `status='rejected'` 은퇴 + 링크 archive, 신규 정의로 같은 이름 재신설(086 전례). 측정 체계가 바뀐 시계열을 한 신호에 섞지 않는다. prod 확인 결과 audit 신호에 confirmed 링크 0(최대 e=6.4)이라 ADR-0048 D2의 re-baseline·강등 공지 의무는 발생하지 않는다.

### 7. 생성일 코호트 추적 기반 — 운명 view (가설 레이어는 #574)

일정 단위 궤적을 한 곳에서 조회하는 view(가칭 `schedule_fate`)를 제공한다: 생성일(KST 코호트 날짜)·카테고리·순미룸 일수·최종 상태(완료/진행/삭제). 살아있는 일정(schedules)과 삭제된 일정(tombstone)을 합집합으로 커버 — 한 번도 안 옮긴 채 조용히 완료된 일정도 코호트의 "잘 해결된" 쪽으로 포함된다(생존 편향 방지). 검증 엔진 통합(코호트 신호 정의·성숙 기간·e-value 정합)은 [#574](https://github.com/hyewon3938/slack-ai-agents/issues/574)에서 설계 — 그 전에도 view로 ad-hoc 추적·주간 리뷰 소비가 가능하다.

## Alternatives considered

### A. 이벤트 단위 측정 유지 + 통계 레이어에서 흡수

- 장점: 마이그레이션 불필요, 누적 e-value 보존
- 단점: 측정 오염은 하류에서 교정 불가(GIGO). 왕복이 만든 가짜 발화일은 Fisher 2×2에 그대로 들어감
- 기각 이유: #504 핵심 원칙 ①(측정 타당성은 통계 신뢰성의 선행조건)과 정면 충돌

### B. 방향무관 순변위 단일 신호로 회귀

- 장점: 신호 1개로 단순
- 단점: 미룸과 당김은 반대 의미 — 합산하면 off-day 대조 무의미화
- 기각 이유: ADR-0046 §1이 이미 기각한 안의 재제안

### C. 앱 레벨 writer 확장 (봇 함수에 기록 INSERT 추가)

- 장점: 로직이 TypeScript 코드에 남아 가시적, DB 트리거 미도입
- 단점: 에이전트 `modify_db`(LLM 자유 SQL) 경로는 여전히 누락 — 대화로 일정을 옮기면 구멍 재발. writer가 늘 때마다 기록 코드 복제 필요
- 기각 이유: 누락 재발을 구조적으로 막지 못함

### D. 생성 당일 전체 유예

- 장점: 늦은 오기입 교정까지 커버(추가 8건)
- 단점: 6시간 이상 경과 후 변경 17건(전형적 진짜 미룸)까지 제거 — 신호 손실이 오염 제거보다 큼
- 기각 이유: prod 분포가 반증. 30분 밖 교정은 의도 데이터 없이는 미룸과 구분 불가능한 랜덤 노이즈로 수용

### E. CASCADE 수용 (이력 소멸 감수)

- 장점: 스키마 불변
- 단점: 연쇄 미룸 끝 포기-삭제가 미룸 데이터의 가장 정보량 높은 케이스인데 소급 소멸
- 기각 이유: 보존 비용(컬럼 1개 + FK 정책)이 데이터 가치 대비 미미

### F. 순변위 + 트리거 단일화 + 로그화 보존 (선택)

- 장점: 왕복·교정·경로 비대칭·소멸·윈도우 5종을 계기 하나(트리거)와 신호 정의 교체로 일괄 해소. 통계 스택 불변. 코호트 캡처(#574 선행)까지 같은 계기에 얹힘
- 단점: 신호 이력 리셋(최대 e=6.4 유실), 트리거 2종 추가로 스키마 복잡도 증가

### G. FK `ON DELETE SET NULL` (인터뷰 초안)

- 장점: 행은 남기면서 참조 무결성 형식 유지
- 단점: 삭제 시 그 일정의 모든 audit 행이 한꺼번에 `schedule_id=NULL` — 삭제 일정들의 이력이 서로 구분 불가능한 한 그룹으로 병합. 순변위의 (일정×하루) 그룹핑이 삭제 후 비결정적으로 붕괴, 코호트 추적 불가
- 기각 이유: 보존이라는 목표는 같지만 보존"만" 되고 식별이 죽는다 — 요구 추가(#574)로 결함이 드러나 로그화(FK 제거)로 교체

## Consequences

### 장점

- 모든 날짜 변경 경로가 단일 계기로 기록 — "웹 사용일" 교란 제거
- off-day 대조(헌장 ②)의 정직성 회복: 당김 발화일 23% 오염 제거, 측정 불가 시기 결측 처리
- 삭제 생존 이력 + tombstone으로 "미루다 포기" 운명이 처음으로 측정 가능 — 생성일 코호트 가설(#574)의 데이터 축적이 배포일부터 시작

### 단점 / 제약

- 기록 로직이 DB로 이동 — 코드만 읽어서는 안 보임 (도메인 문서에 명시로 상쇄)
- 신호 3개의 누적 검증 이력 리셋 — enrollment 클립(ADR-0048)에 따라 재발굴 링크는 등록 익일부터 검정
- 30분 유예 밖의 늦은 오기입 교정은 미룸으로 남음 — 의도 없이는 구분 불가, 수용
