# 0066. SQL 도구 입력 검증의 토큰 기반 분석

- Status: Accepted
- Date: 2026-11-25
- Related: #661, #662, ADR-0001, ADR-0004
- Tags: security, data, agent

## Context

봇의 LLM은 `query_db`와 `modify_db` 도구로 SQL을 직접 작성하고(ADR-0001), 코드가 실행 전에 그 SQL을 검사한다. 검사는 문자열에 정규식을 적용하는 방식이었는데, SQL은 주석, 문자열 리터럴, 따옴표 식별자, 서브쿼리가 섞여 있어서 문자열 패턴보다 토큰 단위로 읽을 때 쿼리 구조를 정확히 알 수 있다. 일정 제목처럼 문자열 리터럴 안에 든 단어 때문에 정상 쿼리가 거절되는 경우도 있었다.

분석 쿼리가 늘면서 JOIN, 서브쿼리, CTE, 집합 연산으로 여러 테이블을 함께 읽는 쿼리가 많아졌고, 사용자 조건을 테이블 단위로 확인하려면 쿼리 구조를 읽는 검사가 필요했다.

웹 대시보드가 쓰는 DB 프록시(ADR-0004)는 별도의 문자열 검사를 갖고 있어서, 두 검사의 해석 기준도 하나로 맞출 필요가 있었다.

## Decision

SQL을 먼저 토큰으로 나눈 뒤, 토큰 열에서 쿼리 구조를 읽어 검사한다.

- `sql-lexer.ts`가 SQL을 단어, 숫자, 문자열, 식별자, 연산자 토큰으로 나눈다. 주석과 문자열 리터럴은 이 단계에서 구분되어 뒤 단계의 판단에 섞이지 않는다. 해석하지 못하는 입력은 통과시키지 않고 거절한다.
- `user-scope.ts`와 `user-scope-dml.ts`가 쿼리가 읽거나 바꾸는 테이블을 블록(SELECT 하나, 서브쿼리 하나, CTE 하나) 단위로 모으고, 테이블마다 `user_id = N` 조건이 그 블록에 보장되는지 확인한다. `OR`로 묶여 조건이 보장되지 않으면 조건이 없는 것으로 본다.
- `user_id`를 현재 사용자 이외의 값과 비교하거나 `=` 이외의 연산자로 다루는 쿼리는 거절한다.
- `sql-guards.ts`가 조회 도구에 들어온 변경 구문, 시스템 함수 호출, 허용하지 않는 테이블 접근을 토큰 기준으로 거절한다.
- 사용자 컬럼이 없는 테이블은 `user-scope.ts`의 목록 세 개로 관리한다. 설정 테이블은 조건 확인에서 면제하고, 공용 조회 테이블은 읽기만 면제하며 변경 대상으로는 받지 않고, 도구가 다루지 않는 테이블은 접근 자체를 거절한다.
- 변경 도구가 대상으로 삼을 수 있는 테이블은 public 스키마로 한정한다.
- 마이그레이션 파일에서 사용자 컬럼이 없는 테이블을 구해 위 목록과 비교하는 테스트를 둬서, 테이블을 추가할 때 목록이 함께 바뀌게 한다.
- DB 프록시의 검사도 같은 렉서를 써서 주석과 문자열을 가린 뒤 패턴을 본다.
- 프롬프트에 적는 SQL 예시가 이 검사를 통과하는지 테스트로 고정해서, 규칙과 예시가 따로 바뀌지 않게 한다.
- 조회 도구는 검사를 통과한 쿼리를 읽기 전용 트랜잭션에서 실행하고 끝나면 항상 롤백한다. 변경 여부는 DB가 한 번 더 판단한다.

판단이 애매한 쿼리는 거절한다. 거절된 쿼리는 LLM이 오류 메시지를 보고 다시 작성하므로, 정상 쿼리를 가끔 거절하는 쪽이 허용 범위를 넓게 잡는 쪽보다 비용이 작다.

## Alternatives considered

### A. 정규식 검사 보강

- 장점: 코드가 짧고 의존성이 없다.
- 단점: 패턴을 더할수록 예외가 늘고 읽기 어려워진다.
- 기각 이유: 테이블별 조건 확인처럼 구조를 알아야 하는 검사를 표현할 수 없다.

### B. PostgreSQL 파서 라이브러리로 AST 분석

- 장점: 서버와 같은 문법으로 해석하므로 구조를 가장 정확히 읽는다.
- 단점: 네이티브 또는 WASM 의존성이 붙고, 봇이 도는 VM은 메모리가 작아서 이미지 크기와 빌드 시간이 부담이다. 파서 버전을 DB 버전과 맞춰 관리해야 한다.
- 기각 이유: 봇이 쓰는 SQL은 범위가 좁아서, 모르는 구문을 거절하는 작은 분석기로도 필요한 검사를 할 수 있다.

### C. DB의 행 수준 보안(RLS)에 위임

- 장점: 검사를 DB가 맡으므로 애플리케이션 검사가 틀려도 보호가 유지된다.
- 단점: 연결마다 사용자 설정을 넣어야 해서 커넥션 풀과 프록시 구조를 바꿔야 하고, 크론과 마이그레이션 경로에 예외 정책이 필요하다.
- 기각 이유: 변경 범위가 커서 이번 결정과 분리했다. 애플리케이션 검사와 함께 쓸 수 있는 방법이라 후속 검토로 남긴다.

### D. 토큰 기반 분석 (선택한 안)

- 장점: 의존성 없이 주석·문자열·중첩 구조를 구분하고, 테이블별 조건을 블록 단위로 확인할 수 있다.
- 단점: 직접 관리하는 분석 코드가 생기고, 지원하지 않는 구문은 정상 쿼리여도 거절된다.

## Consequences

### 장점

- 검사가 쿼리 구조를 기준으로 판단하므로 문자열 리터럴이나 주석의 내용이 결과에 영향을 주지 않는다.
- 여러 테이블을 읽는 쿼리에서 테이블마다 조건을 확인한다.
- 봇 도구와 DB 프록시가 같은 렉서를 써서 해석 기준이 하나다.
- 프롬프트 예시와 검사 규칙의 정합을 테스트가 지킨다.

### 단점 / 제약

- `user_id = $1`처럼 파라미터로 쓴 조건과 `user_id::text` 같은 변형은 거절된다. LLM에게는 숫자 리터럴로 쓰도록 프롬프트에서 안내한다.
- 사용자 컬럼이 있는 테이블을 JOIN할 때 조건을 테이블마다 적어야 해서 쿼리가 길어진다.
- 분석기는 스키마를 읽지 않으므로, 사용자 컬럼이 없는 테이블을 새로 추가할 때는 세 목록 중 하나에 넣어야 하고 넣지 않으면 테스트가 실패한다.
- 사용자 컬럼이 없는 테이블만 읽는 쿼리에 `user_id` 조건을 테이블 이름 없이 쓰면 거절된다.
- 렉서는 `standard_conforming_strings = on`을 전제로 문자열을 읽는다.
- 분석기와 DB의 해석이 달라질 수 있는 형태는 정상 쿼리여도 거절한다. 문자열 리터럴을 연달아 쓴 형태, 사용자 컬럼이 있는 테이블에 `*`로 값을 넣는 INSERT, 식이 시작되는 자리가 분명하지 않은 CASE가 여기에 든다. CASE는 괄호로 감싸면 통과한다.

### 후속 작업

- [ ] 배포 뒤 거절 로그를 보고 정상 쿼리가 반복해서 거절되는 구문이 있으면 프롬프트 예시나 분석기를 보완
- [ ] 행 수준 보안을 함께 쓰는 방안 검토
- [ ] 도구 전용으로 권한을 줄인 DB 역할을 두는 방안 검토
