# 0061. 루틴 추적 모드 이원화 — 기대된 발생과 자발적 기록의 분리

- Status: Accepted
- Date: 2026-07-26
- Related: #604, #605
- Tags: routine, data-model, measurement

## Context

루틴 도메인에는 문서화되지 않은 암묵 계약이 하나 있다. **`routine_records`의 한 행 = 그날 기대된 발생.** 템플릿의 빈도(매일 / 격일 / N일마다 / 주1회)를 보고 봇 크론과 웹이 해당 날짜의 행을 미리 만들어 두고, 사용자가 체크하면 `completed`를 켠다. 그래서 "그날 행 수"가 분모, "완료된 행 수"가 분자로 성립한다.

이 계약 위에 여러 층이 서 있다.

- 봇 아침·밤 크론 통계, 주간 리포트, 인사이트 감지기, 기간 해석 집계, 루틴 맥락 조회
- 웹 통계 (기간별 달성률, 루틴별 달성률, 히트맵)
- DB에 저장된 패턴 신호 정의 SQL — 루틴 완료율·분류별 완료율·연속 달성 계열. 이 신호들은 #477 검증 엔진의 off-day 대조와 확정 게이트(n\~20)에 그대로 투입된다

여기에 **주기가 없는 루틴**을 넣어야 한다. 등록만 해두고 수행한 날에만 기록을 남기는 형태이고, 필요한 분석은 "언제 했는지"와 "이번 달 몇 번" 둘뿐이다. 제약은 네 가지였다.

1. 같은 루틴이 시기에 따라 주기형 ↔ 자율로 오갈 수 있어야 하고, 사용자 입장에서는 계속 하나의 루틴으로 보여야 한다
2. `frequency`는 CHECK 제약이 없는 자유 TEXT 컬럼이다 — 새 값을 여기에 얹으면 타이포를 막을 장치가 없다
3. `routine_records`에는 하루 1건을 보장하는 유니크 제약이 아예 없다 (`sleep_records`에는 있다)
4. 주기 없는 기록이 같은 테이블에 들어가는 순간, 위 모든 층의 분모 정의가 조용히 바뀐다. 특히 기존 운동 루틴을 자율로 전환하는 것만으로도 이미 축적 중인 신호의 의미가 흔들린다

즉 이것은 기능 추가 문제가 아니라 **측정 계약을 명시화하는 문제**다.

## Decision

루틴의 "주기 여부"를 템플릿의 축으로, "그 기록이 어떤 성격이었는지"를 기록의 스탬프로 분리해 저장한다.

```sql
-- 정의: 이 루틴을 어떤 방식으로 추적하는가 (현재 상태, 변경 가능)
ALTER TABLE routine_templates
  ADD COLUMN tracking_mode TEXT NOT NULL DEFAULT 'scheduled'
    CHECK (tracking_mode IN ('scheduled', 'free'));

-- 사실: 이 기록은 어떤 성격으로 생겼는가 (생성 시점 확정, 불변)
ALTER TABLE routine_records
  ADD COLUMN entry_type TEXT NOT NULL DEFAULT 'scheduled'
    CHECK (entry_type IN ('scheduled', 'free'));

-- 주기형은 하루 1건 보장, 자율은 하루 여러 건 허용
CREATE UNIQUE INDEX routine_records_scheduled_daily_uniq
  ON routine_records (user_id, template_id, date)
  WHERE entry_type = 'scheduled';
```

여기서 파생되는 규칙 세 가지가 이 결정의 실체다.

1. **자동 생성은 `scheduled` 템플릿만.** 자율 루틴은 미리 만들어지는 행이 없다. 사용자가 기록한 시점에 `completed = true`, `entry_type = 'free'`로 INSERT된다. 미완료 자율 기록이라는 상태는 존재하지 않는다.
2. **기록의 성격은 소급 변경하지 않는다.** 오늘 모드를 바꿔도 과거 행의 `entry_type`은 그대로다. 작년에 매일 하기로 약속했던 기간의 달성률은 계속 그 약속대로 계산된다.
3. **기대된 발생을 세는 모든 집계는 `entry_type = 'scheduled'`만 본다.** 자율 기록은 분자도 분모도 아니다. 자율 루틴에는 달성률이라는 개념 자체를 적용하지 않는다.

사용자가 느끼는 "같은 루틴"은 템플릿 행이 유지되는 것으로 보장된다. 모드 전환은 컬럼 값 하나를 바꾸는 일이므로 기록·히트맵·메모·soft delete가 전부 끊기지 않고 이어진다.

## Alternatives considered

### A. `frequency`에 `'자율'` 센티널 값 추가

- 장점: 마이그레이션이 사실상 없다. 기존 빈도 판별 함수에 분기 하나만 추가하면 된다.
- 단점: `frequency`는 CHECK 없는 자유 TEXT라 오타 방지 장치가 없다. 결정적으로 **과거 기록이 어느 시대의 것인지 구분할 수 없다** — 기록에는 성격 정보가 남지 않고 현재 모드만 존재하기 때문이다.
- 기각 이유: 모드를 바꾸면 과거 달성률의 의미가 소급으로 뒤집힌다. 제약 1(전환 가능)을 만족시키려다 제약 4(측정 보존)를 깨는 안이다.

### B. 별도 테이블 · 별도 도메인 신설

- 장점: 기존 루틴 집계를 한 줄도 건드리지 않는다. 자율 기록만의 스키마를 자유롭게 설계할 수 있다.
- 단점: 요구의 무게중심이 "전환"인데, 별도 테이블은 전환할 때마다 정체성을 애플리케이션 코드로 봉합해야 한다. 패턴 검증 엔진의 도메인 매핑(`BEHAVIOR_SIGNAL_DOMAIN`·`DOMAIN_TABLE`)에 새 항목을 추가해야 하고, 히트맵·메모·soft delete·비활성 기간처럼 이미 깔린 배관을 전부 다시 깔아야 한다.
- 기각 이유: 비용이 이득을 넘는다. 게다가 "기존 집계를 안 건드린다"는 장점이 허상이다 — 기존 운동 루틴을 자율로 옮기는 순간 어느 안을 택했든 완료율의 분모 정의는 바뀌므로, 측정 격리 작업은 어차피 필요하다.

### C. `tracking_mode` 컬럼 + `entry_type` 기록 스탬프 (선택)

- 장점: 템플릿 행이 전환을 넘어 살아남으므로 사용자 정체성이 데이터 모델 차원에서 공짜로 유지된다. 기록은 각자 자기 시대의 성격을 갖는다. 기존 신호 SQL은 조건 한 줄로 교정되며, 대부분의 시드 SQL이 `routine_records` 단독을 조회하기 때문에 JOIN을 새로 추가할 필요조차 없다. 부분 유니크 인덱스를 넣는 과정에서 주기형 쪽의 하루 1건 보장이 처음으로 DB 수준에 생긴다(제약 3 해소).
- 단점: 컬럼 2개가 늘고, 기대된 발생을 세는 모든 소비처에 조건 하나가 붙는다. 앞으로 새 집계를 추가할 때 이 조건을 빠뜨리면 오염이 재발한다.

## Consequences

### 장점

- 과거 데이터의 의미가 고정된다. 모드 전환이 소급 왜곡을 만들지 않는다
- 사용자 관점의 "하나의 루틴"이 UI 봉합이 아니라 데이터 모델의 자연스러운 결과가 된다
- 주기형 기록의 하루 1건 보장이 DB 제약으로 생긴다 — 지금까지 없던 안전망
- 자율 기록은 하루 여러 건이 허용되므로 "이번 달 몇 번"이 실제 횟수를 반영한다

### 단점 / 제약

- **집계 조건 누락 위험이 영구히 남는다.** 새 루틴 집계·신호를 만들 때 `entry_type = 'scheduled'`를 잊으면 조용히 오염된다. 도메인 문서에 규칙으로 명시하고, 신호 SQL 리뷰 시 점검 항목으로 둔다
- **부분 유니크 인덱스는 기존 중복이 없어야 생성된다.** 지금까지 제약이 없었으므로, 마이그레이션 적용 전에 같은 `(user_id, template_id, date)` 중복 존재 여부를 먼저 확인해야 한다
- **주기형 루틴을 전부 자율로 옮기면 루틴 완료율 신호가 휴면 상태가 된다.** 기대된 발생이 0인 날의 완료율은 0으로 측정되고, `below_avg` 방향에서는 평균도 0이라 아무것도 발화하지 않는다. 거짓 신호를 만들지는 않지만 그 축의 검증이 멈춘다는 뜻이다
- **자율 모드에서 의미 없이 남는 컬럼이 생긴다.** `frequency`는 주기형으로 되돌릴 때를 위해 값을 보존하고, `start_date`·비활성 기간은 UI에서 숨기지만 데이터는 남는다. 전환을 왕복하면 예전 비활성 기간이 되살아난다
- 자율 루틴은 측정값(거리·시간·강도)을 담지 않는다. 담아야 할 요구가 생기면 루틴 확장이 아니라 별도 도메인으로 검토한다
