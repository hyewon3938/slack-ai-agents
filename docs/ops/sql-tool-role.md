# SQL 도구 전용 DB 역할

> 최종 갱신: 2026-11-25
> 관련: [ADR-0067](../adr/0067-sql-tool-db-role.md), [설계 노트](../design-notebook/sql-tool-db-role.md)

LLM이 작성한 SQL은 `query_db`와 `modify_db`를 거쳐 봇 안의 두 번째 연결 풀에서 실행되고, 이 풀은 권한을 줄인 전용 DB 역할로 접속한다. 이 문서는 운영자가 그 역할을 한 번 만들고 서버에 연결 문자열을 등록하는 절차를 적는다.

역할을 만든 뒤 테이블과 시퀀스 권한은 봇이 시작할 때마다 `src/shared/sql-tools/table-permissions.ts`의 목록대로 맞추므로, 운영자는 역할과 비밀번호, 연결 문자열만 관리하면 된다.

---

## 1. 역할 설정 값

역할 이름은 `sql_tool`을 기본값으로 쓴다. 봇은 연결 문자열의 사용자 이름을 역할 이름으로 읽기 때문에 다른 이름을 써도 된다.

| 항목 | 값 |
|------|-----|
| 속성 | `LOGIN`, `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOREPLICATION`, `NOBYPASSRLS`, `NOINHERIT` |
| 소속 역할 | 없음 |
| 연결 수 제한 | 5 |
| `statement_timeout` | 10초 |
| `lock_timeout` | 3초 |
| `idle_in_transaction_session_timeout` | 30초 |
| 데이터베이스 권한 | `CONNECT`. `PUBLIC`의 `TEMPORARY` 권한은 거둔다 |
| 스키마 권한 | `public`에 `USAGE`. `PUBLIC`의 `CREATE` 권한은 거둔다 |

`statement_timeout`은 코드의 `SQL_TIMEOUT_MS`와 같은 값이다. 도구 연결은 쿼리가 끝나면 `RESET statement_timeout`으로 이 기본값으로 돌아간다.

---

## 2. 역할 만들기

`scripts/create-sql-tool-role.sh`가 위 설정을 한 번에 적용한다. DB 컨테이너가 떠 있는 서버에서 저장소 루트를 기준으로 실행한다.

```bash
./scripts/create-sql-tool-role.sh            # 역할 이름 sql_tool
./scripts/create-sql-tool-role.sh my_role    # 역할 이름 지정
```

- 관리 역할과 DB 이름은 환경변수 `POSTGRES_USER`, `POSTGRES_DB`에서 읽고, 없으면 저장소 루트의 `.env`에서 읽는다.
- 컨테이너 이름은 `DB_CONTAINER`로 바꿀 수 있고 기본값은 `slack-ai-agents-db`다.
- 역할 이름이 앱 역할과 같으면 실행을 멈춘다.
- 이미 역할이 있으면 속성과 기본값만 다시 맞추므로 몇 번을 실행해도 결과가 같다.

### 비밀번호

스크립트는 터미널에서 실행하면 마지막에 `psql`의 `\password` 명령으로 비밀번호를 묻는다. `\password`는 클라이언트에서 비밀번호를 해시한 뒤 서버로 보내므로 평문이 명령 기록이나 서버 로그에 남지 않는다.

터미널이 아닌 곳에서 실행했거나 비밀번호를 바꿀 때는 직접 실행한다.

```bash
docker exec -it slack-ai-agents-db psql -U <관리 역할> -d <DB 이름> -c '\password sql_tool'
```

비밀번호는 저장소, 이슈, 채팅에 적지 않는다.

## 3. 서버 환경변수 등록

서버의 환경 파일에 도구 역할의 연결 문자열을 넣는다. 호스트와 포트, DB 이름은 `DATABASE_URL`과 같고 사용자와 비밀번호만 다르다.

```
SQL_TOOL_DATABASE_URL=postgresql://sql_tool:<비밀번호>@<호스트>:<포트>/<DB 이름>
```

등록한 뒤 봇 컨테이너를 다시 만들어야 새 환경변수를 읽는다. 저장소의 `.env.example`에는 키 이름만 있다.

운영 이미지는 Dockerfile에서 `NODE_ENV=production`을 넣어 두기 때문에, 운영에서 이 환경변수가 없으면 봇은 시작은 하되 SQL 도구와 신호 측정 SQL 실행을 거절한다. 거절할 때 LLM은 도구 실행 오류를 돌려받고, 일정 알림 같은 다른 기능은 평소대로 돈다. 로컬 개발(`yarn dev`)과 테스트에서는 `NODE_ENV`가 `production`이 아니어서 기존 연결 풀로 대신 실행하고 경고만 남긴다.

서버 환경 파일에 `NODE_ENV`를 다른 값으로 넣으면 컨테이너 설정이 이미지 값을 덮어 필수 동작이 꺼진다. 운영에서는 `NODE_ENV`를 환경 파일에 넣지 않고, 시작 로그의 `(운영 필수: true)`로 확인한다.

## 4. 봇이 시작할 때 하는 일

봇은 마이그레이션을 끝낸 뒤 권한 동기화를 실행하고, 동기화에 성공했을 때만 도구 풀을 연다. 동기화는 한 트랜잭션 안에서 도구 역할의 `public` 테이블·시퀀스·함수 권한을 모두 거둔 뒤 목록대로 다시 준다.

도구 쪽 어느 단계가 실패해도 봇은 그대로 시작한다. 동기화를 건너뛰거나 실패하면 도구 풀을 열지 않으므로, 연결 문자열이 넓은 속성의 역할을 가리켜도 그 역할로 SQL이 실행되지 않는다. 도구 풀이 열리지 않았을 때 운영에서는 SQL 도구와 신호 측정 SQL 실행을 거절하고, 로컬에서는 기존 연결 풀로 대신 실행한다.

신호 측정 SQL은 주간 검증 엔진이 신호마다 날짜별로 실행하는데, 거절된 날은 값이 없는 날로 처리하기 때문에 엔진 전체는 멈추지 않는다. 매일 아침 패턴 매칭도 실패한 지표만 빼고 나머지 지표를 평가한다. 확인 카드의 실행 버튼도 같은 도구 풀에서 실행하므로, 거절 상태에서는 카드에 실행 실패가 표시되고 대기 중인 변경은 다시 누를 수 있게 남는다.

도구 연결 상태는 시작 로그의 `SQL 도구 전용 역할 연결: true (운영 필수: true)` 한 줄로 확인한다. 앞의 값은 권한 동기화와 도구 풀 연결이 모두 성공했을 때만 `true`다. 같은 값은 DB 프록시의 `/health` 응답에 `sqlToolRole` 불린으로도 나온다.

시작 로그는 `[SQL 권한]`과 `[DB]`로 시작한다. 아래 표의 문구는 운영 기준이고, 로컬에서는 `SQL 도구 실행을 거절합니다` 대신 `SQL 도구가 기존 연결 풀을 씁니다`가 찍힌다.

| 시작 로그 | 상황 | 할 일 |
|-----------|------|-------|
| `도구 역할 권한 동기화 완료`, `SQL 도구 전용 풀 연결 완료`, `SQL 도구 전용 역할 연결: true` | 목록대로 권한을 맞추고 도구 풀을 열었다 | 없음 |
| `SQL 도구 전용 역할 연결: false (운영 필수: true)`, `운영 환경에 SQL 도구 전용 연결이 없어 SQL 도구와 신호 측정 SQL 실행을 거절합니다` | 운영에서 도구 풀이 열리지 않아 SQL 도구를 거절하고 있다 | 같이 찍힌 아래 로그로 원인을 찾아 고친다 |
| `역할이 DB에 없어 건너뜀`, `도구 역할 권한을 맞추지 못해 SQL 도구 실행을 거절합니다` | 연결 문자열의 역할이 DB에 없다. 도구 풀을 열지 않는다 | 2장 절차로 역할을 만든다 |
| `도구 역할 권한 동기화 완료`, `SQL 도구 전용 풀 연결 실패, SQL 도구 실행을 거절합니다` | 권한은 맞췄지만 비밀번호가 틀렸거나 접속할 수 없다 | 2장의 `\password`로 비밀번호를 다시 정하고 3장의 연결 문자열을 맞춘다 |
| `앱 역할과 같은 역할이라 건너뜀` | 연결 문자열이 앱 역할을 가리킨다. 도구 풀을 열지 않는다 | 3장의 연결 문자열을 고친다 |
| `슈퍼유저·RLS 우회 속성이 있는 역할이라 건너뜀`, `public 테이블을 소유한 역할이라 건너뜀` | 도구 역할에 넓은 속성이 있거나 테이블을 소유한다. 도구 풀을 열지 않는다 | 2장 스크립트를 다시 실행하고, 소유한 테이블이 있으면 앱 역할로 소유자를 옮긴다 |
| `도구 역할 권한 동기화 실패` | 동기화 SQL이 실패해 트랜잭션이 롤백됐다. 도구 풀을 열지 않는다 | 에러 내용을 보고 원인을 고친다 |
| `목록에 있지만 DB에 없는 테이블`, `목록에 없어 권한을 주지 않은 테이블` | 마이그레이션과 권한 목록이 다르다. 동기화는 진행한다 | 권한 목록에 테이블을 더하거나 뺀다 |
| `SQL_TOOL_DATABASE_URL이 없어 SQL 도구 실행을 거절합니다` | 환경변수가 없다 | 3장 절차로 등록한다 |

원인을 고친 뒤에는 봇을 다시 시작하고 `SQL 도구 전용 역할 연결: true`가 찍혔는지 확인한다.

---

## 5. 백업을 복원한 뒤

`scripts/restore-db.sh`는 권한 정보를 빼고 복원하므로 복원 직후 도구 역할의 테이블 권한이 비어 있다. 역할 자체와 비밀번호는 DB 클러스터에 남아 있어 다시 만들 필요가 없고, 봇을 다시 시작하면 동기화가 권한을 되돌린다. 절차는 [db-backup.md](./db-backup.md) 4장에도 있다.

DB 컨테이너의 데이터 볼륨까지 새로 만든 경우에는 역할도 사라지므로 2장부터 다시 한다.

## 6. 권한 확인

필요할 때 관리 역할로 접속해 도구 역할의 권한을 본다.

```sql
SELECT table_name, string_agg(privilege_type, ', ' ORDER BY privilege_type)
  FROM information_schema.role_table_grants
 WHERE grantee = 'sql_tool'
 GROUP BY table_name ORDER BY table_name;
```

쓰기 권한이 있는 테이블은 권한 목록의 10개뿐이어야 하고, `users`, `pending_modify`, `slack_user_mappings`, `schema_migrations`와 뷰 3개는 결과에 나오지 않아야 한다. `notification_settings`의 `time_value`와 `schedule_changes`의 삭제 사유 컬럼처럼 컬럼 단위로 준 UPDATE는 이 쿼리에 나오지 않고 `information_schema.column_privileges`에서 보인다.
