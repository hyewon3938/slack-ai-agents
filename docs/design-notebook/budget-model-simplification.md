# 예산 모델 단순화 (Budget Model Simplification)

> 지출/예산 도메인의 묶인 돈·자산 모델을 단일 원리로 재정렬하는 마스터.
> 관련 도메인: [budget](../domains/budget.md) · 관련 ADR: [0051](../adr/0051-budget-model-simplification-runway-locked.md)

## 핵심 원칙 (헌장 — 모든 phase가 이 위에서)

이 마스터의 모든 결정은 아래 4개 위에서 진행한다. 바뀌어야 하면 ADR부터.

1. **reservation과 depletion은 별개의 동작이다.**
   - reservation = 미래 의무를 자유 예산에서 미리 빼두는 것(라이브 계산, 자금값 불변).
   - depletion = 실제 결제가 일어나 자금이 줄어드는 것(결제주기 정산 1곳).
   - 이 둘을 한 메커니즘에 섞으면(과거 "등록 시점 자산 차감") 수기 갱신과 충돌해 깨진다. 항상 분리.

2. **묶인 돈은 목표 기간(target_date) 창 기준으로 일괄 처리한다.**
   - 창 = `[현재 결제월, target_date]`. 창 안의 할부·고정비·예정지출이 묶인 돈.
   - 창 밖(target_date 이후)은 예산에서 제외 — "그 이후는 별도 처리" 전제.
   - 건별 의도 구분 없음. 모든 묶인 돈을 동일 규칙으로.

3. **자금은 단일 필드, 입력 의미는 "현금 유동자금" 하나다.**
   - 사용자 입력 = 통장 잔액 − 지난 결제 대금. 그 외 계산(고정비·할부 차감)은 시스템 몫.
   - 사용자에게 "미래 할부를 직접 빼서 넣어라" 요구 금지.
   - **개정 (Phase 2, ADR [0062](../adr/0062-payment-method-withdrawal-timing.md))**: 입력 의미가 **"기준일 시점의 통장 잔액 그대로"** 로 단순해진다. 뺄 것을 사용자가 계산하지 않는다 — 시스템이 기준일 기준으로 복원한다.

4. **사용자 입력이 시스템 자동값과 충돌하면 사용자 입력이 승.**
   - 자동 차감은 편의(정산 시 자금 추적)일 뿐, 최종 권위는 사용자 수기 보정.
   - 따라서 reservation은 자금값에 의존하지 않게 설계(라이브 계산)해 충돌해도 안 깨지게.

> **불변식**: 한 할부 회차는 "결제 전엔 reservation, 결제 후엔 depletion + 창 이탈"의 생애를 가지며 이중 카운트되지 않는다.

## Phase 1 — 모델 재정렬 (#539)

### 배경 / 문제

묶인 돈(할부) 반영이 4경로로 분산돼 있었다: ① 등록 시점 자산 즉시 차감(ADR 0015) ② 건별 `distribute_to_runway` 토글(ADR 0018) ③ allocator 현재월 락 ④ `exclude_from_budget` 할부의 정산-전용 처리(사각지대). 자산이 수기 갱신 전제로 동작하는데, 사용자가 자산을 직접 입력하면 ①의 미래 회차 차감이 덮어써지고 ③은 현재월만 반영하므로 **목표기간 창 안 미래 할부가 자유 예산에서 누락**됐다. 자유 예산·일 예산이 과대 계상되는 증상.

근본 원인: reservation과 depletion을 "등록 시점 자산 차감" 한 메커니즘에 혼재.

### 결정 (요약)

ADR [0051](../adr/0051-budget-model-simplification-runway-locked.md):

- 자금 단일화(비상금 제외) — 입력 의미 "현금 유동자금"
- 묶인 돈 = 목표기간 창 안 [할부 회차 + 고정비 + 예정지출] 일괄 (`billing_month` 기준)
- 건별 토글(`distribute_to_runway`, 할부 exclude) 제거. target_date 변경 시 자산 보정 로직 제거
- 할부 1회차도 묶인 돈(현재월 락) — `flexibleSpent`에서 할부 전체 제외 → "오늘 예산"에 안 몰리고 현재 주기 자유 예산 전체를 깎음
- depletion 일원화: 등록 시점 차감 제거, 결제주기 정산에서 **그 주기 전체 결제분** 차감(기존 `flex+excluded` 누락분 해소)

### 인터뷰 분기점 (이 phase에서 고른 안)

- **할부 1회차 처리**: "전부 묶인 돈"으로 가되, 1회차가 "오늘 예산"엔 안 빠져도 **현재 주기 자유 예산 전체는** 깎이게 → 1회차를 현재월 락에 귀속(flex 제외)하는 방식으로 충족. (대안: 1회차만 자유지출 유지 = 모델 덜 단순, 기각)
- **자금 자동차감**: 순수 수기 대신 **자동 차감 + 수기 보정** 채택. 단 헌장 4(사용자 입력 승)로 충돌 안전성 확보.
- **목표기간 만료**: 자동 롤링/N개월 창 대신 **수동 연장 + 임박 경고** 채택. "언제까지 버티나" 목표 의미 보존 우선.
- **비상금(투자 자산)**: 자금에 합치지 않고 **분리 유지** — 예산 분배에서 빠져야 "최후의 보루" 의미가 사는 점.

### 포기한 안 (재제안 금지)

- ADR 0015·0018 유지 + 수기 갱신 시 재차감 보정 → 분산 복잡도 증가, 근본원인 미해결로 기각.
- 할부를 결제일 기준 정산만으로 처리(reservation 폐기) → 미래 할부가 자유 예산에 안 보여 과대 인식, 기각.

### 기술적 의의

- 4경로 → 1경로(목표기간 창 라이브 계산) 수렴. 토글 UI·자산 보정·변경 모달 등 대량 코드 삭제.
- reservation/depletion 분리를 명시 원칙으로 승격 — 회계 모델의 두 축을 코드 구조로 반영.

> 자세한 어필 표현·면접 답변 초안은 portfolio-candidates(비공개)에.

### 결과 (구현 완료)

- 4경로 → 1경로 수렴 완료. 묶인 돈 = `[현재월, target]` 창 안 `billing_month`별 할부 락(`readInstallmentLockByMonth`), depletion = 정산 시 전체 결제분(`readTotalCycleSpent`).
- 자금 단일화 마이그레이션 `092_consolidate_funds_asset.sql` (플래그 기반·이름/금액 하드코딩 없음). 적용 후 자금 1회 재입력.
- 토글 UI·자산 보정 4함수·변경 모달 대량 삭제. `distribute_to_runway`는 데드 컬럼으로 보존(드롭 안 함).
- 전체 269 테스트 통과. reservation/depletion 분리·이중카운트 부재를 테스트로 고정.

### 미해결 / 후속

- 목표 기간 만료 임박 경고 UI 디테일 (현재 배너만).
- 향후 지출 로직 재설계(별도 트랙) 진입 시 헌장 1\~4 재확인.

## Phase 2 — 결제수단별 출금 시점 (#615)

### 배경 / 문제

Phase 1은 depletion을 결제주기 종료 정산 1곳으로 모았다. 이 모델은 **모든 결제수단이 후불**이라는 전제 위에 선다. 카드는 사용 시점에 통장 잔액이 안 줄어드니 "주기 끝에 한꺼번에 나간다"가 맞는 근사다.

실제로는 즉시 출금되는 수단(현금·계좌이체)이 섞여 있다. 이 지출은 기록 시점에 이미 통장에서 나갔다. 헌장 3은 이 간극을 자금 **입력 의미**("통장 잔액 − 지난 결제 대금")로 흡수하려 했지만, 두 가지로 깨졌다.

1. **주기 도중 갱신에서 이중 차감.** 사용자는 경계에서만 잔액을 갱신하지 않는다. 도중에 넣은 잔액엔 이번 주기 즉시 출금분이 이미 빠져 있는데, 예산은 그 지출을 자유지출·묶인 돈으로 다시 뺀다.
2. **결과가 입력 시점에 의존.** 같은 재정 상태인데 주기 초에 넣은 잔액과 주기 말에 넣은 잔액이 서로 다른 하루 예산을 만든다.

역설이 하나 있다. 이 이중 차감은 시스템이 혼자 굴러갈 땐 안 생긴다(정산은 결제월당 1회 멱등). **사용자가 성실하게 잔액을 갱신할수록** 어긋난다.

수입에는 같은 결함이 반대 방향으로 있었다. 월 배분기는 이번 주기 수입이 자금에 이미 있다고 전제하고 배분만 조정하는데(총액 중립), 정산은 같은 수입을 자금에 한 번 더 더한다.

그 아래에 **고정비 결제수단 부재**가 깔려 있다. `fixed_costs`에 결제수단 컬럼도, 설정 화면 필드도 없어서 자동 기록이 매달 특정 카드로 하드코딩된다. 실제로 현금으로 나가는 고정비를 사용자가 매 주기 손으로 고쳐야 했다.

### 결정 (요약)

ADR [0062](../adr/0062-payment-method-withdrawal-timing.md):

- 결제수단에 **출금 시점**(`immediate` / `deferred`) 속성 부여. 정의를 한곳으로 모으고 카드 대금기간을 여기서 파생. 미등록 수단은 `deferred`(보수적 기본값)
- 자금에 **기준일**(`balance_as_of`) 추가 — "이 잔액은 며칠까지 반영된 값인가"
- **예산 기준선 복원**: 저장 잔액 + (이번 주기 `immediate` 지출 중 기준일 이전 && 예산이 별도로 차감하는 항목). 예산이 애초에 안 세는 지출은 복원 안 함
- **정산은 미반영분만**: 결제분 전체 − 이미 나간 전액 / 수입 전체 − 이미 들어온 몫. 정산 후 기준일을 주기 종료일로 이동
- `fixed_costs.payment_method` 추가 + 설정 UI 노출
- `source='fixed'` 지출의 예산제외 잠금을 **키 존재**가 아니라 **값 변경** 기준으로 판정 (금액만 고치는 저장이 막히던 것 해소)
- **예산 산식·`billing_month` 귀속 규칙·과거 데이터는 무변경**

### 인터뷰 분기점 (이 phase에서 고른 안)

- **자금 반영 시점**: 사용자가 먼저 제안한 "즉시 출금 지출은 기록 시 자금에서 바로 차감"이 회계적으로 자연스러웠으나, 예산 표시 모델("자유 예산 총액 − 쓴 만큼")과 충돌해 이중 차감이 재현되는 것을 도출 → **기준일 + 기준선 복원**으로 선회. 예산 층은 결제수단을 구분하지 않는다는 경계를 지키는 쪽.
- **범위**: 과거 주기 소급은 **제외**(사용자 명시). 우선순위는 "이번 주기부터 자유 예산·하루 예산이 맞게 나오는 것".
- **정산 장부 정리**: 스냅샷 이월 체인이 실제 자금과 벌어져 있으나 **기준선 1회 정렬**로 축소. 체인 재계산은 소급이라 범위 밖.
- **미등록 결제수단 기본값**: `immediate`가 아니라 **`deferred`**. "이미 나갔다"가 틀리면 자금이 과대 계상되고, 과대 계상은 과소 계상보다 위험하다.

### 포기한 안 (재제안 금지)

- **지출 기록 시 즉시 자금 차감** → 이중 차감의 발생 지점을 옮길 뿐 없애지 못한다. 피하려면 자유지출 집계에서 현금을 빼야 하고, 그러면 "이번 달 얼마 썼나"가 결제수단에 따라 달라진다. 기각.
- **자금 입력 시점에 복원값을 확정 저장** → 저장 후 그 주기 지출을 고치면 기준선이 안 따라간다. 정확성이 사용자의 재입력 습관에 의존하는데, 그 습관 위에 얹은 전제가 깨져서 생긴 문제다. 기각.
- **카드 실제 결제일까지 모델링** → 기준일이 있으면 그 어긋남은 다음 잔액 입력에서 흡수된다. 비용 대비 이득 낮음, 이번 범위 밖.
- **현행 유지(사용자 수기 보정)** → 헌장 3이 이미 택했고 깨진 안.

### 기술적 의의

- 예산 층과 자금 층의 책임을 분리. 결제수단 구분은 자금 층에만 두고, 예산 층은 결제수단을 모르는 현행을 유지한다.
- 저장값(통장 잔액)과 계산값(예산 기준선)을 나누고 그 사이를 **기준일**이라는 단일 좌표로 잇는다 — 입력 시점 독립성이 규율이 아니라 구조로 보장된다.
- 사용자가 손으로 하던 보정을 없애는 방향으로 결함을 해소. 헌장 4(사용자 입력 승)는 유지되지만, 애초에 보정할 게 없어진다.

> 자세한 어필 표현·면접 답변 초안은 portfolio-candidates(비공개)에.
