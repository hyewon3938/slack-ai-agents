# 수면 인사이트 강화 — 점수 다각화·입력 정밀화·대시보드 확장

> 마스터 이슈: #588
> 시작: 2026-07-10
> 상태: 진행 중

## 개요

수면 기록(취침/기상/중간기상/낮잠/메모)은 꾸준히 쌓이는데 활용 층이 얇았다. 점수는 취침시각 표준편차 하나(규칙성)뿐이고, 슬랙 자연어 입력은 명시 날짜 소급 기록·낮잠/밤잠 경계에서 오기록이 났고, 분할 수면(한 밤을 여러 구간으로 끊어 기록)은 대시보드 집계에서 유실됐고, 대시보드는 조회 전용이었다.

이 마스터는 기존 기록 항목만으로 수면의 질을 4축+종합으로 점수화하고, 입력 정확도를 프롬프트 규칙으로 끌어올리고, 대시보드에서 직접 기록까지 가능하게 만든다. 파생 점수는 저장하지 않고 원본에서 결정론 계산해 패턴 검증 시스템(signal_defs)에도 같은 방식으로 연결한다.

## 핵심 원칙

> 마스터 전체 phase가 이 위에서 진행. 변경하려면 ADR.

1. **점수는 저장하지 않는다** — 원본(sleep_records/sleep_events)에서 결정론 재계산으로 파생. 웹은 API 응답에서 계산, 통계는 signal_defs SQL로 계산. 일별 파생값 저장 컬럼을 의도적으로 폐기한 기존 아키텍처(마이그 078)를 계승한다.
2. **임의값은 코드에 박지 않는다** — 목표 구간·가중치·경계값 전부 상수 모듈로 외부화하고 ADR에 근거를 남긴다 (#434 헌장 ⑤ 적용).
3. **세그먼트가 1급 개념** — 밤잠 = 같은 date의 night 레코드 집합. 합성 규칙(시작=첫 취침, 종료=마지막 기상, 구간 갭=수면 중 각성)은 웹·봇·통계가 공유하는 단일 의미론이다. 짧은 각성(수 분)은 sleep_events, 긴 각성은 세그먼트 분리 — 두 신호를 합쳐 분절도를 측정한다.
4. **memo 원문은 통계에 노출하지 않는다** — 특이사항은 고정 태그 어휘로 구조화해서만 통계 연계 (v2 헌장 ① 상속). memo 자유텍스트는 사람용으로 병행 유지.
5. **슬랙 입력은 자유 자연어 유지** — fast path 정규식 부분추출 금지 원칙 준수. 정확도는 프롬프트 규칙(명시 날짜 few-shot, 낮잠 판정, 세그먼트 기록)으로 확보한다.

## 전체 Phase 흐름

- [x] Phase 1: 점수 4축+종합, 세그먼트 합성 집계, 대시보드 개편, 탭 순서, 스키마 정비 (#589, 2026-07-11 머지+배포)

## Phase 1: 점수 체계 + 세그먼트 집계 + 대시보드 개편 (2026-07-10)

- 이슈: #589
- 관련 ADR: ADR-0059
- 관련 계획서: `.claude/plans/589-sleep-score-foundation.md`
- 상태: 설계 완료

### 결정 요약

수면 점수를 4축(시간·규칙성·연속성·타이밍)+종합으로 확장한다. 전부 기존 기록만으로 계산 가능하고, DB 저장 없이 웹 API 응답에서 파생한다. 같은 날 night 레코드 여러 개를 "세그먼트"로 합성하는 집계를 도입해 분할 수면 유실 버그(마지막 레코드가 덮어쓰는 문제)를 고치고, 부산물로 수면 효율(누운 시간 대비 실제 수면)까지 얻는다. 스키마는 sleep_events.user_id(nullable 추가)와 sleep_records.tags만 정비하고, NOT NULL 승격은 봇 프롬프트가 user_id를 쓰기 시작하는 Phase 2로 미룬다.

### 의사결정 분기점

- **점수 축 구성**: 3축(타이밍 제외) / 4축 / 5축(주관 질 포함) 검토 → 4축 채택. 타이밍(취침 절대 시각)과 규칙성(흩어짐)은 측정 대상이 다르다 — 매일 새벽 3시에 자면 규칙성 100점이지만 타이밍 0점. 봇의 자정 취침 잔소리 로직과도 일관. 주관 질은 기록 부담 증가라 보류.
- **점수 저장 vs 파생**: 일별 점수 테이블 저장안 기각. 마이그 078이 일별 스냅샷 컬럼을 "원본 재계산이 진실"이라며 폐기한 전례와 충돌하고, 공식 수정 시 과거 데이터 drift 발생. 파생 계산이면 공식 개선이 소급 적용된다.
- **세그먼트 종료 시각 계산**: wake_time 문자열 재파싱 대신 `취침(래핑) + duration_minutes`로 계산. 20:00 경계 래핑 로직이 wake 시각에 오적용되는 엣지(밤늦은 기상)를 원천 회피.
- **규칙성 확장**: 취침 표준편차 단독 → 취침+기상 각각 점수화 후 평균. 기상만 무너지는 패턴(취침은 일정한데 늦잠)을 잡기 위해.
- **낮잠의 점수 반영**: 미반영 유지. 아침잠은 기존대로 밤잠 시간에 합산, 오후 낮잠은 통계 신호(sleep_nap_count)로만 소비. 낮잠을 점수에 벌점화하면 "기록할수록 점수가 깎이는" 역인센티브가 생긴다.

### 포기한 안 / 미룬 항목

- **주관적 수면질(1\~5) 기록**: 미룸. 트리거 = 4축 운영 후 종합점수와 체감 질의 괴리가 반복 관찰되면 5축으로 확장 검토.
- **중간기상 지속시간 기록**: 기각. 사용자 기록 관행이 이미 커버 — 긴 각성(10분+)은 세그먼트 분리로 기록되고, 짧은 각성의 분 단위는 정보 가치 대비 기록 부담(새벽에 시계 확인)이 크다.
- **일별 종합점수**: 미룸. 규칙성이 기간 속성이라 일별 정의가 애매. Phase 1은 기간(1w/2w/1m) 점수만.
- **차트 라이브러리 도입**: 기각. 기존 손수 SVG 관례 유지 — 종합점수 게이지도 인라인 SVG 신규 제작.
- **sleep_events.user_id NOT NULL 즉시 승격**: 미룸(Phase 2). 봇 프롬프트가 아직 user_id 없이 INSERT하므로 Phase 1에서 승격하면 배포 사이 프로덕션 INSERT 실패. nullable 추가+backfill만 하고 승격은 프롬프트 갱신과 같은 PR로.

### 미해결·가설

- **가중치 기본값(시간 0.35 / 규칙성 0.25 / 연속성 0.20 / 타이밍 0.20)은 추정**: 수면 위생에서 총량이 가장 지배적이라는 일반론 기반. 검증 = 운영 2\~4주 후 종합점수가 체감과 어긋나는 주 발견 시 상수 조정 (파생 계산이라 소급 반영됨).
- **기존 데이터의 세그먼트 표현 불확실**: 프롬프트 개선(Phase 2) 전에 기록된 분할 수면이 DB에 2행으로 들어갔는지, 1행+이벤트로 뭉쳐졌는지 미확인 (프로덕션 조회는 /build 시점에 확인). 과거 구간의 연속성 점수는 보수적으로 해석.
- **태그 어휘 초기 10종이 실사용과 맞는지**: memo 실데이터 대조를 /build에서 수행, 어휘는 CHECK 제약이라 확장은 마이그레이션 1개로 가능 (diary meta tag 전례와 동일 경로).

### 회고 (2026-07-11 머지 후)

- **세그먼트 합성이 예상보다 파급이 컸다.** 웹 집계만 고치면 되는 줄 알았는데, 봇의 생활 맥락·추세 감지·주간 리포트·기간 집계·트리거 평가가 전부 "1밤=1행"을 가정하고 있었다. 웹만 세그먼트를 알고 봇은 모르는 반쪽 상태 → Phase 2에서 봇 SQL 전면 정합으로 편입. 세그먼트 의미론을 도메인 헌장(원칙 ③)으로 올린 게 이 전파를 강제하는 앵커가 됐다.
- **분할 수면은 쓰기 시점부터 막혀 있었다.** 정찰에서 발견 — 프롬프트의 중복 방지 규칙(`(date, sleep_type)` 유일성)이 세그먼트 2행 INSERT 자체를 UPDATE로 눌러버렸다. 즉 Phase 1은 "저장은 되는데 집계에서 유실"이 아니라 "애초에 저장이 안 되던" 데이터를 시각화하려던 것. Phase 2 프롬프트에서 `bedtime` 포함 유일성으로 재정의해야 실제 세그먼트가 쌓이기 시작한다 → Phase 1의 세그먼트 렌더는 프롬프트 개선 전까진 대부분 단일 세그먼트만 그린다(가설 검증: 프로덕션 데이터 축적 필요).
- **점수 카드 렌더 검증은 합성 목 데이터로만 했다.** 로컬에 DB 자격증명이 없어 실데이터 경로(API→DB proxy)는 배포 후에만 확인 가능. 게이지·4축·세그먼트 갭·빈 상태까지 목으로 커버했지만, 실제 프로덕션 첫 렌더는 관찰 대상으로 남긴다.
- **PR 머지 직전 main이 움직였다**(#590 일정 삭제, ADR-0060). ADR 인덱스·features.md 충돌 → 두 항목 나란히 보존으로 해소. 마이그 번호도 105(내 것) < 106(#590)로 역전됐지만, 러너가 파일명 단위 추적(high-water-mark 아님)이라 안전함을 코드로 확인하고 진행.

## Phase 2: 슬랙 입력 정밀화 + 봇 세그먼트 정합 + 신호 확장 (2026-07-11)

- 이슈: #593
- 관련 ADR: 없음 (ADR-0059 의미론의 전파. 판정 휴리스틱은 프롬프트 규칙 수준 — 되돌리기 쉬움)
- 관련 계획서: `.claude/plans/593-sleep-input-precision.md`
- 상태: 구현 중

### 결정 요약

Phase 1이 확립한 세그먼트 의미론을 입력·봇·통계 3개 레이어에 전파한다. 슬랙 입력 프롬프트를 재작성해 사용자가 겪던 오인식 3종(명시 날짜 소급 기록, 늦은 낮잠↔밤잠 혼동, 분할 수면 저장 차단)을 규칙으로 해소하고, 봇 SQL 소비자 전체를 날짜별 집계로 통일해 세그먼트 왜곡을 없애고, 통계 신호를 확장(중간기상 횟수·취침 지각)하면서 기존 `sleep_wake_hour`의 분할 수면 왜곡(MIN→MAX)을 교정한다. sleep_events.user_id를 NOT NULL로 승격(프롬프트가 이제 user_id를 씀).

### 의사결정 분기점

- **날짜 판정: 코드 가드 vs 프롬프트 규칙** → 프롬프트 규칙 채택. fast path 정규식 부분추출 금지 헌장(원칙 ⑤)과 "자유언어 키워드 추출 정규식 금지" 피드백에 따라, 명시 날짜 파싱을 코드로 선처리하지 않고 우선순위 규칙 + few-shot으로 LLM이 판정하게 둔다.
- **낮잠 판정: 시각 하드 경계 vs 명시어 우선 휴리스틱** → 명시어 우선 3단계. 순수 시각 경계는 "저녁 9시 낮잠" 같은 경계 케이스를 반드시 틀린다. 명시어 → 시각 휴리스틱(5시간+ 긴 낮잠은 확인) → 애매하면 질문 순.
- **봇 집계 교정 범위: 최소 vs 전면** → 전면(6파일). 웹만 세그먼트를 알고 봇은 모르면 같은 데이터에 두 진실이 생긴다. 단 순수 계산부/쿼리부 분리가 안 된 함수는 무리한 리팩토링 대신 SQL 문자열 검증으로.
- **신호 value_type**: 계획 초안의 `count`는 스키마 CHECK(binary|continuous) 위반 — `continuous`로 교정 (설계 중 스키마 재확인에서 발견).

### 포기한 안 / 미룬 항목

- **중간기상 지속시간 신호**: 기각 유지 (Phase 1과 동일 — 긴 각성은 세그먼트로, 짧은 각성 분 단위는 기록 부담 과다).
- **명시 날짜 코드 파서**: 영구 기각 — 헌장 충돌.
- **홈 뷰(blocks.ts) 세그먼트 표시 개편**: 조회 함수가 세그먼트를 자르지만 않으면 Phase 2 범위 밖 (blocks 렌더 개편은 별도 판단).

### 미해결·가설

- **프롬프트 개선으로 실제 세그먼트가 쌓이는가**: 검증 = 프로덕션 2\~4주 운영 후 같은 date에 night 2행이 실제로 INSERT되는지 확인. 안 쌓이면 프롬프트 few-shot 보강.
- **신호 시드 배선**: 새 신호 2건이 단순 INSERT로 발굴 엔진에 잡히는지, 아니면 pattern_catalog/seed_pool 추가 배선이 필요한지는 구현 중 기존 sleep 신호 등록 경로 대조로 확정.

### 회고 (2026-07-11 머지+배포)

- **신호 테이블이 계획 가정과 달랐다.** 계획서는 `signal_defs`를 가정했지만 정찰 초기엔 마이그 052의 `saju_signal_metrics`가 보였다. 워커가 052→063(rename)→077(이관+원본 DROP)→085(dedup) 이력을 추적해 **현재 살아있는 건 `signal_defs`, saju_signal_metrics는 죽은 테이블**임을 확정. 마이그레이션 아키타이핑은 "최신 파일"이 아니라 "이관 이력 끝"을 봐야 한다는 교훈.
- **`value_type='count'`가 스키마 위반이었다.** 계획 초안이 중간기상 횟수를 count로 잡았는데 CHECK가 binary|continuous만 허용. 설계 중 스키마 재확인으로 continuous 교정. 계획서 숫자를 코드로 옮기기 전 스키마 대조의 가치.
- **마이그 번호가 또 밀렸다.** 계획은 106이었지만 #590이 선점 → 워커가 스스로 107로 채번. 러너가 파일명 단위라 갭은 무해.
- **봇 세그먼트 정합이 6파일 10함수로 번졌다.** Phase 1 회고에서 예고한 "반쪽 상태"를 실제로 메웠다. 특히 `threshold.ts loadSleepMinutes`의 `LIMIT 1`은 분할 수면일에 첫 세그먼트(예: 150분)만 집어 "6시간 미만" 트리거를 잘못 발화시키던 진짜 버그였다 — 시각화 왜곡을 넘어 잘못된 잔소리를 유발하던 지점.
- **마이그 자기검증이 배포 게이트로 작동.** 107이 SQL 실행 스모크 + NOT NULL 정합 DO 블록을 내장해, 배포 성공 자체가 "신호 SQL이 실제 prod 스키마에서 실행 가능 + 승격 완료"의 증거가 됐다(#573 좀비 신호 재발 차단 패턴 계승).

### 결정 요약

슬랙에서만 가능하던 수면 기록을 대시보드에서도 직접 입력하게 한다. 기존 루틴/지출의 5단 쓰기 패턴(Form → hook mutation → API route → queries.ts → DB proxy)을 재사용. 폼은 하루치 수면을 단위로 다루고 분할 수면 세그먼트(여러 밤잠 구간 행)·낮잠·중간기상·태그(고정 10종)·메모를 전부 지원해 슬랙 입력과 동등한 표현력을 준다. duration은 서버가 SQL로 계산(봇과 동일 규율).

### 의사결정 분기점

- **폼 저장 모델: replace-day vs diff**: 단일 사용자·저위험이라 edit 시 replace-day(기존 레코드 삭제 후 재생성) 허용. 행별 diff(PATCH/DELETE/POST)는 복잡도 대비 이득 적음.
- **duration 계산 위치: 서버 vs 클라이언트**: 서버(SQL). 봇 규율(암산 금지)과 통일, 자정 넘김 로직 단일화.
- **tags를 SleepRecord 필수 필드로 승격**: 대시보드가 태그를 표시·편집하려면 조회에도 필요 → 타입 필수화 + 조회 SELECT·픽스처 동시 갱신(green 유지).

### 포기한 안 / 미룬 항목

- **행별 diff 저장**: 미룸. replace-day로 충분. 멀티유저·동시편집 생기면 재검토.
- **태그별 통계 카드**: Phase 3 범위 밖. 태그 데이터가 쌓이면 별도 phase에서 "특이사항→다음날 점수" 상관 카드 검토.

### 미해결·가설

- **로컬 검증 한계**: 로컬에 DB proxy 자격증명이 없어 폼의 실제 쓰기(201)는 배포 후에만 확인. 프리뷰는 렌더·상호작용·POST body 발사까지만 검증.
