# SQL 도구 전용 DB 역할

> 마스터 이슈: #663 (Phase 1 #664, Phase 2 #665)
> 시작: 2026-11-25
> 상태: Phase 1·2 구현 완료, 후속 보류

ADR-0066이 후속 작업으로 남긴 두 항목을 다룬다. 하나는 도구 전용으로 권한을 줄인 DB 역할이고, 다른 하나는 행 수준 보안을 함께 쓸지에 대한 검토다.

## 핵심 원칙

1. **SQL 검사와 DB 권한은 서로 기대지 않는다.** 검사를 통과한 SQL이라도 도구 전용 역할에 권한이 없으면 DB가 거절한다. 검사 규칙이 바뀌어도 권한은 그대로 남는다.
2. **권한은 허용 목록으로 준다.** 새 테이블은 목록에 넣기 전까지 도구 역할이 읽지도 쓰지도 못한다.
3. **권한 목록의 원본은 코드 한 곳이다.** SQL 검사, DB 권한 부여, 테스트가 같은 목록을 읽는다.
4. **비밀번호는 저장소에 들어가지 않는다.** 역할 생성과 비밀번호 설정은 운영자가 직접 하고, 저장소에는 절차와 권한 목록만 둔다.

## 개요

지금은 SQL 도구와 앱의 나머지 기능이 같은 연결 풀을 쓴다. 도구가 실행하는 SQL은 LLM이 쓰므로 ADR-0066의 토큰 기반 검사를 거치는데, 이 검사와 별개로 DB가 한 번 더 판단하게 하려면 도구가 쓰는 연결의 역할부터 달라야 한다.

이 설계는 도구 전용 역할을 만들고, 봇 안에 그 역할로 접속하는 두 번째 연결 풀을 둔다. LLM이 쓴 SQL이 실행되는 지점은 모두 두 번째 풀로 옮기고, 크론과 마이그레이션, 웹 대시보드용 프록시는 기존 풀을 그대로 쓴다.

## 전체 Phase 흐름

| Phase | 내용 | 상태 |
|-------|------|------|
| 1 | 전용 역할과 두 번째 풀 도입, 권한 목록과 동기화, 호출부 전환 | 구현 완료 |
| 2 | 전용 연결 필수화, 신호 측정 SQL 경로 전환 | 구현 완료 |

## Phase 1. 전용 역할과 두 번째 풀

### 결정 요약

#### 연결 방식

봇 안에 두 번째 풀을 둔다. 연결 문자열은 환경변수 `SQL_TOOL_DATABASE_URL`로 받고 풀 크기는 2로 시작한다. 도구 호출은 한 번에 하나씩 순서대로 실행되고 조회와 변경이 겹치는 경우가 드물어 2면 충분하다고 생각했다.

두 번째 풀로 옮기는 호출부는 다음과 같다.

| 호출부 | 지금 쓰는 함수 | 옮기는 시점 |
|--------|----------------|-------------|
| `query_db` 조회 | `queryReadOnlyWithTimeout` | Phase 1 |
| `modify_db` 미리 실행 | `dryRunAffectedRows` | Phase 1 |
| `modify_db` 실행 | `queryWithRowLimit` | Phase 1 |
| 확인 카드의 실행 버튼 | `dryRunAffectedRows`, `queryWithRowLimit` | Phase 1 |
| 신호 측정 SQL | `queryReadOnly` | Phase 2 |

`get_schema`는 고정된 쿼리만 실행하므로 기존 풀에 둔다. 확인 대기 중인 변경을 저장하고 읽는 `pending_modify` 처리도 앱 코드가 쓰는 고정 쿼리라 기존 풀에 둔다.

도구 연결에서는 쿼리마다 `SET statement_timeout = 0`으로 되돌리던 정리 단계를 `RESET statement_timeout`으로 바꾼다. 0으로 되돌리면 역할 기본값으로 걸어 둔 제한 시간까지 풀리기 때문이다.

#### 역할 속성과 기본값

역할 이름은 `sql_tool`을 예시로 쓴다. 실제 이름은 연결 문자열에서 읽으므로 코드에 고정하지 않는다.

| 항목 | 값 |
|------|-----|
| 속성 | `LOGIN`, `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOREPLICATION`, `NOBYPASSRLS`, `NOINHERIT` |
| 소속 역할 | 없음. 기본 제공 역할에도 넣지 않는다 |
| 연결 수 제한 | 5 |
| `statement_timeout` | 10초. 코드의 `SQL_TIMEOUT_MS`와 같은 값 |
| `lock_timeout` | 3초 |
| `idle_in_transaction_session_timeout` | 30초 |
| 데이터베이스 권한 | `CONNECT`만. 임시 테이블 생성 권한은 주지 않는다 |
| 스키마 권한 | `public`에 `USAGE`만. `CREATE`는 주지 않는다 |

역할 속성과 기본값, 데이터베이스 권한은 역할을 만들 때 운영자가 한 번 설정한다. 테이블과 시퀀스 권한은 아래 동기화 단계가 맡는다.

#### 테이블 권한

권한은 세 묶음으로 나눈다. 묶음별 테이블 수는 `docs/code-map/db.md`의 테이블 49개를 기준으로 셌다.

| 묶음 | 대상 | 권한 |
|------|------|------|
| 읽고 쓰기 | 에이전트 프롬프트가 변경 대상으로 안내하는 테이블 10개 | `SELECT`와 테이블별로 필요한 변경 권한 |
| 읽기만 | 사용자 데이터 테이블 가운데 위 10개와 시스템용 2개를 뺀 나머지, 공용 조회 테이블 7개 | `SELECT` |
| 권한 없음 | `users`, `schema_migrations`, `pending_modify`, `slack_user_mappings`, 뷰 3개, 목록에 없는 모든 테이블 | 없음 |

읽고 쓰기 묶음의 테이블별 권한은 다음과 같이 잡는다. 구현 세션이 프롬프트의 SQL 예시와 대조해 확정한다.

| 테이블 | SELECT | INSERT | UPDATE | DELETE |
|--------|--------|--------|--------|--------|
| `schedules` | O | O | O | O |
| `categories` | O | O | O | O |
| `routine_templates` | O | O | O | O |
| `routine_records` | O | O | O | O |
| `sleep_records` | O | O | O | O |
| `sleep_events` | O | O | O | O |
| `reminders` | O | O | O | O |
| `custom_instructions` | O | O | O | O |
| `notification_settings` | O | X | 시간 컬럼만 | X |
| `schedule_changes` | O | O | 삭제 사유 컬럼만 | X |

`schedule_changes`의 `INSERT`는 도구가 직접 쓰는 권한이 아니다. `schedules`를 고치거나 지우면 트리거가 변경 이력을 남기는데, 트리거 함수는 SQL을 실행한 역할의 권한으로 돌기 때문에 도구 역할에 이 권한이 있어야 일정 수정과 삭제가 성공한다.

`pending_modify`를 권한 없음에 둔 이유는 확인 절차의 독립성이다. 확인 카드가 실행할 SQL을 담는 테이블이므로 도구가 쓴 SQL로는 읽거나 바꿀 수 없어야 확인 절차가 SQL 도구와 따로 유지된다.

#### 시퀀스와 함수

- 시퀀스는 `INSERT` 권한을 준 테이블의 것에만 `USAGE`를 준다. `SELECT`와 `UPDATE`는 주지 않는다.
- `public` 스키마의 함수는 `PUBLIC`에서 실행 권한을 거두고 도구 역할에도 주지 않는다. 지금 있는 함수 3개는 모두 트리거 함수이고, 트리거 함수의 실행 권한은 트리거를 만들 때 한 번 확인하므로 도구 역할의 변경 작업에는 영향이 없다고 생각했다. 구현 세션이 로컬 DB에서 일정 수정과 삭제로 확인한다.
- 서버 파일이나 서버 설정을 다루는 내장 함수는 일반 역할에 기본으로 닫혀 있다. 도구 역할을 어떤 역할에도 넣지 않아 이 기본값을 유지한다.
- 그 밖의 내장 함수는 실행 권한을 하나씩 거두지 않는다. 내장 함수 전체를 관리 대상으로 삼으면 PostgreSQL 버전이 오를 때마다 목록을 다시 맞춰야 하므로, 이 범위는 SQL 검사의 함수 규칙과 역할의 제한 시간에 맡긴다.

#### 권한 목록과 동기화

권한 목록은 `src/shared/sql-tools/` 아래 파일 하나에 둔다. 테이블마다 줄 권한을 적고, 권한을 주지 않는 테이블도 "권한 없음"으로 이름을 적는다.

봇은 시작할 때 마이그레이션을 끝낸 뒤 이 목록대로 권한을 맞춘다.

1. 도구 역할이 DB에 있는지 본다. 없으면 경고를 남기고 건너뛴다.
2. 한 트랜잭션 안에서 `public` 스키마의 테이블, 시퀀스, 함수에 걸린 도구 역할의 권한을 모두 거둔다.
3. 목록대로 다시 준다.

이 단계는 몇 번을 실행해도 결과가 같다. 백업을 복원하면 복원 스크립트가 권한 정보를 빼고 되살리기 때문에 도구 역할의 권한이 사라지는데, 봇을 다시 시작하면 같은 단계가 권한을 되돌린다.

SQL 검사의 변경 대상 판단도 같은 목록을 읽게 한다. 검사는 통과했는데 DB가 거절해 LLM이 권한 오류 문구를 받는 경우를 줄이고, 목록을 두 군데서 따로 관리하지 않기 위해서다.

#### 새 테이블이 생길 때

CI에는 DB가 없으므로 정적 테스트로 지킨다. `sql-table-scope.test.ts`가 이미 마이그레이션 파일에서 테이블을 뽑아 검사 목록과 비교하고 있어 같은 방식에 검사를 더한다.

- 마이그레이션에 있는 모든 테이블이 권한 목록에 한 번씩 나온다. 새 테이블을 만들고 목록에 넣지 않으면 테스트가 실패한다.
- 변경 권한을 준 테이블은 모두 SQL 검사가 변경을 허용하는 테이블이다.
- 조회 권한을 준 테이블은 모두 SQL 검사가 조회를 허용하는 테이블이다.
- SQL 검사가 거절하는 테이블은 권한 목록에서 "권한 없음"이다.
- 목록에서 GRANT 문을 만드는 함수는 DB 없이 문자열로 검증한다.

#### 역할 생성 경로

| 환경 | 방법 |
|------|------|
| 운영 | 운영자가 `docs/ops/`의 절차대로 한 번 실행한다. 비밀번호는 `psql`의 `\password` 명령으로 직접 입력하고, 연결 문자열은 서버의 환경 파일에만 넣는다 |
| 로컬 | 같은 절차를 담은 스크립트를 `scripts/`에 두고 개발자가 직접 실행한다. 비밀번호는 실행할 때 입력한다 |
| CI | 역할을 만들지 않는다. DB가 없으므로 위 정적 테스트만 돈다 |

`\password`는 비밀번호를 클라이언트에서 해시한 뒤 서버로 보내므로 평문이 서버 로그나 명령 기록에 남지 않는다.

`.env.example`에는 `SQL_TOOL_DATABASE_URL` 키 이름만 더한다.

#### 환경변수가 없을 때

Phase 1에서는 `SQL_TOOL_DATABASE_URL`이 없으면 기존 풀로 대신하고 시작 로그에 경고를 남긴다. 로컬 개발과 테스트가 역할 없이도 돌고, 운영에서는 환경변수를 등록하기 전에 머지해도 봇이 뜬다. Phase 2에서 운영 필수로 바꾼다.

### 의사결정 분기점

#### 두 번째 풀과 `SET ROLE`

같은 풀에서 `SET ROLE`로 역할을 바꾸는 방식은 연결 문자열이 하나로 유지되고 비밀번호가 필요 없다는 장점이 있다. 다만 역할을 바꾼 세션은 원래 역할로 되돌아갈 수 있어서, 두 역할을 나누는 근거가 SQL 검사에 다시 기대게 된다. 핵심 원칙 1과 맞지 않아 두 번째 풀을 택했다.

두 번째 풀의 비용은 연결 2개와 환경변수 1개, 운영자 절차 1회다.

#### 권한 부여 위치

| 방식 | 판단 |
|------|------|
| 봇 시작 시 동기화 | 채택. 복원 뒤에도 자동으로 맞춰지고 목록이 코드 한 곳에 있다 |
| 마이그레이션 파일에 GRANT | 기각. 역할이 없는 DB에서는 마이그레이션이 실패해 봇이 뜨지 못하고, 복원 뒤에는 이미 적용된 파일이라 다시 실행되지 않는다 |
| `ALTER DEFAULT PRIVILEGES` | 기각. 새 테이블에 한꺼번에 권한이 붙어 허용 목록 원칙과 반대로 간다 |

#### 쓰기 권한의 범위

SQL 검사는 사용자 데이터 테이블 전부를 변경 대상으로 받는다. DB 권한을 같은 범위로 줄 수도 있지만, 에이전트 프롬프트가 변경을 안내하는 테이블은 10개뿐이다. 쓰지 않는 권한을 열어 둘 이유가 없어 10개로 좁혔다. 좁힌 범위 때문에 막히는 요청이 나오면 목록에 한 줄을 더해 푼다.

### 포기한 안·미룬 항목

- **조회용과 변경용 역할 분리.** 조회 도구는 이미 읽기 전용 트랜잭션에서 실행하고 항상 롤백한다. 역할을 둘로 나누면 풀과 절차가 하나씩 더 늘어 얻는 것에 비해 관리할 것이 많다.
- **뷰 조회 권한.** 뷰 3개는 Phase 1에서 권한을 주지 않는다. 뷰는 만든 역할의 권한으로 기반 테이블을 읽기 때문에 테이블 권한 목록과 따로 판단해야 한다. 에이전트가 뷰를 쓰는지 확인한 뒤 필요하면 더한다.
- **행 수준 보안.** 지금은 도입하지 않는다. 아래 "행 수준 보안 검토"에 근거를 적었다.
- **웹 대시보드 프록시 전용 역할.** 프록시는 웹의 고정 쿼리를 받아 실행하고 다루는 테이블 범위가 SQL 도구와 다르다. 권한 목록을 따로 설계해야 해서 이 마스터에서 다루지 않는다.

### 미해결·가설

- 풀 크기 2가 실제 사용에서 충분한지는 배포 뒤 대기 로그로 확인한다.
- `notification_settings`에 도구가 `INSERT`하는 경우가 있는지 프롬프트와 대조해야 한다. Phase 1에서 대조한 결과 알림 프롬프트가 슬롯 추가를 막고 있어 `INSERT`는 주지 않았고, Phase 2에서 `UPDATE`도 `time_value` 컬럼으로 줄였다.
- `schedule_changes`의 `UPDATE`를 컬럼 단위로 줄 때 대상 컬럼 이름은 구현 세션이 정한다.
- 트리거 함수가 `schedule_changes` 말고 다른 테이블을 건드리는지 구현 세션이 함수 본문을 읽고 확인한다.
- 실제 DB에 권한을 적용한 뒤 거절을 확인하는 통합 테스트는 CI에 DB가 없어 로컬 확인 절차로만 둔다. CI에 DB 서비스를 붙일지는 따로 판단한다.

## Phase 2. 전용 연결 필수화와 신호 측정 SQL

### 결정 요약

- 운영에서 `SQL_TOOL_DATABASE_URL`이 없으면 SQL 도구가 실행을 거절하고 오류를 돌려주게 바꾼다. 기존 풀로 대신하는 동작은 로컬 개발과 테스트에만 남긴다.
- 신호 측정 SQL도 두 번째 풀에서 실행한다. 이 경로가 읽는 테이블은 `signal-sql-guard.ts`의 허용 목록 10개이고 모두 Phase 1의 조회 권한 안에 있다.
- 시작 로그와 `/health` 응답에 도구 연결이 전용 역할로 붙었는지를 참·거짓 값으로 낸다.

### 구현 결과

- **운영 판단 기준은 `NODE_ENV=production`이다.** 운영 이미지의 Dockerfile 실행 단계에 이 값을 넣어 두어, 운영자가 따로 등록할 값 없이 이미지가 운영 여부를 정한다. 로컬 `yarn dev`에서는 값이 비어 있고 테스트에서는 `test`라서 기존 풀로 대신하는 동작이 그대로 남는다. 별도 환경변수를 두면 운영 서버의 환경 파일에 하나를 더 등록해야 하고, 빠뜨리면 거절하지 않고 기존 풀로 조용히 실행되기 때문에 이 방식을 택했다. 서버 환경 파일에 `NODE_ENV`를 다른 값으로 넣으면 이미지 값을 덮으므로, 운영 문서에 시작 로그로 확인하는 절차를 적었다.
- **거절은 도구 풀을 얻는 함수 한 곳에서 한다.** 운영 필수 상태에서 도구 풀이 없으면 이 함수가 전용 오류를 던지고, 조회·변경·변경 전 행 수 확인·신호 측정 네 경로가 모두 이 함수를 거친다. 에이전트 루프는 이 오류를 도구 실행 오류로 LLM에 돌려주고, 확인 카드 실행 버튼은 대기 중인 변경을 다시 누를 수 있게 둔 채 실행 실패를 표시한다. 연결 문자열이 없을 때, 권한 동기화를 건너뛰거나 실패했을 때, 연결에 실패했을 때 모두 도구 풀이 열리지 않으므로 같은 규칙을 따른다.
- **신호 측정 SQL은 도구 풀의 읽기 전용 트랜잭션에서 실행한다.** 타임아웃, 행 수 제한, 항상 롤백하는 동작과 `$1`·`$2` 문자열 치환은 그대로 두고, 실행 뒤 타임아웃을 0으로 바꾸던 정리를 `RESET`으로 바꿔 도구 역할의 기본 타임아웃이 유지되게 했다. 주간 검증 엔진은 날짜별로, 아침 패턴 매칭은 지표별로 실패를 따로 처리하기 때문에 거절 상태에서도 엔진 전체는 멈추지 않는다.
- **거절은 결측과 다르게 다룬다.** 처음에는 거절된 날을 값이 없는 날로 처리했는데, 그러면 예측 채점이 측정 불가로 확정되고 주간 결과가 비어 저장된다. 그래서 거절 오류만 시리즈 계산 밖으로 올려 보내고, 받은 쪽은 그 LLM 신호를 이번 실행에서 건너뛰어 기존 행을 건드리지 않는다. 다음 실행이 다시 측정한다. 로그는 실행 단계마다 한 번만 남긴다. 아침 패턴 매칭은 발현 여부를 아침 카드가 쓰므로 행은 기록하되, 통과한 지표 없이 건너뛴 시드의 매칭 결과는 미채점(null)으로 둔다. 재기준선 스크립트도 봇처럼 도구 풀을 연다.
- **상태 표시는 불린 하나다.** 시작 로그의 `SQL 도구 전용 역할 연결: true/false (운영 필수: true/false)`와 DB 프록시 `/health` 응답의 `sqlToolRole`은 권한 동기화와 도구 풀 연결이 모두 성공했을 때만 `true`다. 역할 이름과 오류 내용은 넣지 않았다. 운영 필수 상태에서 `false`면 거절 중이라는 에러 로그를 한 줄 더 남긴다.
- **`notification_settings` UPDATE를 `time_value` 컬럼으로 줄였다.** 알림 프롬프트가 슬롯은 고정이고 시간만 바꿀 수 있다고 안내하기 때문에, SQL 검사와 DB 권한 둘 다 다른 컬럼 변경을 거절한다.

### 미해결·가설

- 운영 환경을 가리는 기준은 위 구현 결과대로 `NODE_ENV=production`으로 정했다.
- 풀 크기 2를 채팅의 SQL 도구와 주간 신호 측정이 함께 쓴다. 신호 측정은 순서대로 실행하지만, 배포 뒤 대기 로그로 부족한지 확인한다.
- `notification_settings`의 `active` 컬럼은 이제 도구로 바꿀 수 없다. 알림을 켜고 끄는 요청이 생기면 권한 목록에 컬럼을 더한다.

### 후속 정리 (#669)

- 연결을 빌려 쓰는 쿼리 헬퍼 여섯 개의 정리 단계를 `db.ts`의 공통 헬퍼 하나로 모았다. ROLLBACK이나 제한 시간 원복이 실패하면 상태를 알 수 없는 연결이라 풀에 되돌리지 않고 폐기한다. 앱 풀을 쓰는 `queryWithClient`도 원복을 `RESET`으로 맞췄다.
- 조회 범위 분석기 `user-scope.ts`를 공용 규칙, FROM 목록 해석, 범위 보장 확인의 세 파일로 나눴고, 기존 import 경로는 다시 내보내기로 유지했다. 변경문 대상 테이블 앞의 `LATERAL`은 해석을 거절하도록 했다.

## 행 수준 보안 검토

이번에는 도입하지 않고 전용 역할까지만 한다.

| 근거 | 내용 |
|------|------|
| 사용자 수 | 사용자가 사실상 1명이라 행을 사용자별로 가르는 정책이 지금 막아 주는 범위가 좁다 |
| 관리 부담 | 사용자 데이터 테이블마다 정책을 두고 새 테이블마다 더해야 한다 |
| 사용자 값 전달 | 정책이 현재 사용자를 알려면 연결마다 값을 넣어야 한다. 세션 설정값에 기대는 정책은 SQL 검사와 같은 전제에 놓여 핵심 원칙 1이 약해진다 |
| 도입 비용의 변화 | 전용 역할이 생기면 정책 적용 대상이 그 역할 하나로 좁아져, 나중에 도입할 때 크론과 마이그레이션 경로를 건드릴 일이 줄어든다 |

다시 검토하는 시점은 사용자가 2명 이상이 되는 때다. 그때는 사용자마다 DB 역할을 따로 두는 방식과 함께 비교한다.

## ADR

Phase 1 세션이 ADR 1건을 쓴다. 전용 역할과 두 번째 풀, 권한 동기화 방식, 행 수준 보안 보류를 한 건에 담고 번호는 구현 세션이 정한다. 되돌리기 어렵고 대안이 있었으며 근거가 자명하지 않아 작성 기준에 든다.
