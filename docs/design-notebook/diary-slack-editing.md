# Slack 일기 수정

> 마스터 이슈: [#639](https://github.com/hyewon3938/slack-ai-agents/issues/639)
> 시작: 2026-10-22
> 상태: 설계 완료, 구현 대기

## 핵심 원칙

> 이 기능의 기준. 구현 중에 원칙을 바꿔야 하면 ADR부터 쓴다.

1. 일기는 **쓰는 곳인 Slack에서 고친다**. 웹 대시보드에는 일기 화면이 없어서, 조회한 메시지에서 바로 수정 화면을 열도록 했다.
2. **메타 태그는 일기 원문을 따라간다**. 사용자가 고친 내용이 그날의 사실이므로, 원문이 바뀐 날짜의 태그는 지우고 다시 추출한다. 지난 날짜의 검증 수치가 조금 달라질 수 있지만, 틀린 일기로 만든 태그를 남겨 두는 쪽이 측정을 더 해친다고 생각했다.
3. **수정, 날짜 이동, 삭제를 모달 하나에서 처리한다**. 삭제 버튼은 따로 두지 않고, 내용을 전부 비우고 저장하면 그 날짜 일기를 지운다.
4. **모달에 쓴 글은 그대로 저장한다**. 채널에 쓰는 일기와 같은 규칙이라 LLM 정리를 거치지 않는다.

## 개요

인사이트 채널에 쓴 일기는 날짜별로 `diary_entries`에 한 행씩 저장되고, 같은 날 다시 쓰면 기존 일기 뒤에 이어 붙는다. 저장한 일기를 고치는 명령은 없어서 오타를 고치거나 날짜를 잘못 붙인 일기를 옮기려면 DB를 직접 고쳐야 한다. 그래서 조회 명령으로 일기를 띄우고, 그 메시지의 수정 버튼으로 모달을 열어 내용과 날짜를 한 번에 고치도록 설계했다. 봇에서 Slack 모달을 쓰는 건 이번이 처음이라 모달을 열고 제출을 받는 코드도 함께 만든다.

### 결정 요약

사용자는 아래 순서로 일기를 고친다.

1. `오늘 일기`나 `10/21 일기`를 보내면 봇이 그날 일기와 수정 버튼 1개를 보낸다.
2. 버튼을 누르면 위에는 날짜 선택, 아래에는 원문이 채워진 내용 입력칸이 있는 모달이 열린다.
3. 저장하면 봇이 원래 조회 메시지를 고친 내용으로 바꾸고 짧은 확인 문구를 보낸다.

**조회 명령**

- `M/D 일기`는 메시지 전체가 이 형식일 때만 조회로 받는다. 날짜는 날짜 지정 일기와 같은 `resolveDiaryDate`로 정해서, 오늘을 포함해 그 이전의 가장 가까운 M/D가 된다.
- 날짜 지정 일기 저장보다 먼저 검사한다. 순서가 바뀌면 `10/21 일기`가 `일기` 두 글자짜리 10/21 일기로 저장된다.
- 그날 일기가 없으면 없다고만 답하고 버튼은 붙이지 않는다.

**모달 구성**

- 날짜는 datepicker로 고르고, 처음 값은 지금 일기의 날짜다.
- Slack 입력칸 하나가 3000자까지만 받아서, 긴 일기는 줄 경계에서 나눠 입력칸 여러 개에 담는다. 줄바꿈 없이 3000자를 넘는 줄만 글자 수로 자른다. 입력칸 사이가 원래 줄바꿈이었는지 바로 이어진 글이었는지를 `private_metadata`에 적어 두고, 저장할 때 같은 방식으로 다시 붙인다.
- 마지막 입력칸이 2000자를 넘으면 빈 입력칸을 하나 더 둬서 내용을 늘릴 수 있게 한다.
- `private_metadata`에는 일기 id, 원래 날짜, 모달을 열 때의 원문 해시, 조회 메시지의 채널과 ts, 입력칸 연결 정보를 넣는다.

**저장 규칙**

- 미래 날짜를 고르면 저장하지 않고 날짜 선택에 오류를 띄운다. 기준은 날짜 지정 일기와 같은 달력 기준 오늘(KST)이다.
- 모달을 연 뒤 같은 날 일기를 채널에 이어 썼거나 에이전트가 이어 붙여서 원문이 바뀌었으면, 저장하지 않고 모달을 다시 열어 달라는 오류를 띄운다. 열 때 적어 둔 원문 해시와 저장 직전의 원문 해시를 비교해서 판단한다.
- 날짜를 그대로 두면 내용만 바꾼다.
- 날짜를 바꿨을 때 그 날짜에 일기가 없으면 행의 날짜만 바꾼다. 일기가 있으면 그 일기 뒤에 줄바꿈으로 이어 붙이고 원래 행은 지우는데, 두 작업은 트랜잭션 하나로 처리한다.
- 입력칸을 전부 비우고 저장하면 원래 날짜의 일기를 지운다. 날짜를 바꾼 채로 비워도 같고, 확인 단계는 두지 않는다.
- 버튼을 누른 Slack 사용자로 소유자를 다시 확인하고, 모든 쿼리에 `user_id` 조건을 건다.

**메타 태그**

- 원문이 바뀐 날짜의 `diary_meta_tags`는 `source`와 상관없이 지운다. 날짜를 옮기면 원래 날짜와 새 날짜가 모두 해당한다.
- 태그를 지운 날짜에 일기가 남아 있고 그 날짜가 생활 기준 오늘보다 앞서면, 날짜 지정 일기와 같은 `backfillDiaryMetaTags`로 바로 다시 추출한다. 봇은 추출을 백그라운드로 돌리고 바로 답한다. 생활 기준 오늘의 일기는 다음 날 05:30 추출 cron이 처리한다.
- `seed_daily_activations`는 다시 계산하지 않는다. 아침 카드에 넘겨 주는 기록이라 지난 날짜 값이 남아도 검증 결과에는 영향이 없고, 주간 검증 엔진은 매번 원본 테이블에서 다시 계산한다.

### 의사결정 분기점

- **수정 화면을 여는 곳**: (a) 일기를 저장할 때마다 확인 메시지에 버튼 / (b) 조회 메시지에만 버튼 → **(b) 채택**. 일기는 대화하듯 자주 쓰는데 저장할 때마다 버튼이 붙으면 채널이 버튼으로 가득 찬다. 고칠 일이 생겼을 때 조회해서 여는 것으로 충분하다고 생각했다.
- **입력 방식**: (a) `10/21 일기 수정 …` 같은 텍스트 명령 / (b) 모달 → **(b) 채택**. 텍스트 명령은 고칠 부분을 포함해 일기 전체를 다시 써야 하고, 긴 일기는 메시지 하나로 다시 보내기도 어렵다. 모달은 원문이 채워진 채로 열려서 틀린 글자만 고치면 된다.
- **버튼 수**: 수정 버튼과 날짜 변경 버튼 2개 / 날짜와 내용을 함께 담은 모달 하나 → **하나 채택**. 날짜를 옮기면서 내용도 고치는 경우가 많고, 버튼이 하나면 조회 메시지도 단순해진다.
- **옮길 날짜에 일기가 있을 때**: (a) 저장 거부 / (b) 덮어쓰기 / (c) 뒤에 이어 붙이기 → **(c) 채택**. 같은 날 두 번 쓰면 이어 붙이는 채널 저장 규칙과 같아서 결과를 예상하기 쉽고, 어느 쪽 내용도 잃지 않는다. 순서를 바꾸고 싶으면 옮긴 뒤 다시 열어 고치면 된다.
- **삭제 방법**: 별도 삭제 버튼 / 내용을 비우고 저장 → **후자 채택**. 내용을 비우고 저장하는 방식이면 실수로 지울 일이 적고, 지우려는 사람은 내용을 직접 비우는 동작을 거쳐야 한다.
- **3000자를 넘는 일기**: (a) 수정 불가로 안내 / (b) 앞부분만 수정 / (c) 입력칸 여러 개에 나눠 담기 → **(c) 채택**. 실제로 3000자를 넘는 일기가 있어서 그 일기만 못 고치면 기능이 반쪽이 된다. 입력칸 경계를 줄바꿈에 맞추면 사용자에게는 문단이 나뉜 것처럼 보인다.
- **원문 변경 감지**: `updated_at` 비교 / 원문 해시 비교 → **해시 채택**. 에이전트가 일기를 이어 붙일 때는 프롬프트 규칙으로 `updated_at`을 갱신하는데, 모델이 이를 빠뜨리면 비교 코드가 변경을 놓친다. 원문 자체를 비교하면 어떤 경로로 바뀌었든 잡을 수 있다.
- **메타 태그 처리**: (a) 그대로 둔다 / (b) 새로 나온 태그만 더한다 / (c) 지우고 다시 추출한다 → **(c) 채택**. (a)는 고친 내용과 태그가 다른 채로 검증에 들어가고, (b)는 지운 내용에서 나온 태그가 남는다. 일기는 하루 1행이라 그날 태그를 통째로 다시 만드는 비용이 작다. 지난 날짜 태그가 바뀌면 주간 검증 수치도 다음 계산부터 달라지는데, 엔진이 매주 원본에서 다시 계산하므로 따로 보정하지 않는다. 지난 측정값을 바꾸는 판단이라 ADR로 남긴다.

### 포기한 안 / 미룬 항목

- 웹 대시보드의 일기 수정은 일기 화면부터 새로 만들어야 해서 미뤘다.
- `어제 일기` 명령은 `M/D 일기`로 같은 일을 할 수 있어서 미뤘다.
- 삭제 확인 단계와 수정 이력 보관은 실사용에서 잘못 지운 일이 생기면 다시 판단한다. 지운 일기도 채널에 처음 쓴 메시지가 남아 있어서 그 글로 다시 쓸 수 있다.
- 대화로 일기를 고치는 방식은 자유 문장에서 날짜와 고칠 내용을 뽑아야 해서, 정해진 명령만 받는 fast path 원칙과 맞지 않아 범위에서 뺐다.

### 미해결 / 가설

- 05:00\~05:30 사이에 어제 일기를 고치면 바로 추출하는 쪽과 05:30 cron이 같은 날짜를 두 번 추출한다. 태그 저장이 중복 행을 무시해서 행이 겹치지는 않지만, 두 번의 결과가 다르면 둘을 합친 태그가 남는다. 드문 시간대라 그대로 둔다.
- 모달은 버튼을 누른 뒤 3초 안에 열어야 한다. 조회 쿼리 1번이면 충분하다고 가정하고, 열기 실패는 오류 로그로 확인한다.
- 입력칸 여러 개로 나눈 일기를 경계 근처에서 고쳤을 때 다시 붙인 결과가 자연스러운지는 실사용으로 확인한다.
