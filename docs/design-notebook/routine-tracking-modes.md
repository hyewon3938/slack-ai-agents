# 자율 루틴 — 루틴 추적 모드 이원화

> 마스터 이슈: [#604](https://github.com/hyewon3938/slack-ai-agents/issues/604)
> 시작: 2026-07-26
> 상태: 진행 중

## 핵심 원칙

> 이 마스터의 헌장. 모든 phase는 이 위에서 진행하고, 원칙을 바꿔야 하면 ADR부터 쓴다.

1. **하나의 루틴, 여러 시대** — 루틴의 정체성은 템플릿 행(`template_id`)이 보장한다. 추적 모드가 바뀌어도 행은 유지되고, 기록·히트맵·메모는 끊기지 않는다. 사용자에게 "같은 루틴"으로 보이는 것은 UI 봉합이 아니라 데이터 모델의 결과여야 한다.
2. **기록의 성격은 불변** — 어떤 기록이 "기대된 발생"이었는지 "자발적 기록"이었는지는 생성 시점에 결정되고 소급 변경하지 않는다. 오늘 모드를 바꿨다고 작년 달성률의 의미가 달라지면 안 된다.
3. **분모는 기대된 발생만** — 달성률·연속 달성 계열은 `entry_type = 'scheduled'`만 센다. 자율 기록은 분자도 분모도 아니다. 자율 루틴에는 달성률이라는 개념 자체를 적용하지 않는다. (#477 헌장 ② "신호는 시드와 무관하게 매일 일관되게 측정"의 직접 상속)
4. **자율 루틴은 횟수와 날짜만** — 측정값(거리·시간·강도)을 담지 않는다. 담고 싶어지는 순간 그것은 루틴이 아니라 운동 로그이고, 다른 도메인의 설계 대상이다.

## 개요

기존 루틴은 전부 주기형이다. 템플릿에 빈도를 두고, 봇 크론과 웹이 그날 해당하는 기록 행을 미리 만들어 둔 뒤 사용자가 체크하면 완료로 바꾼다. 이 구조에서 `routine_records`의 한 행은 "그날 기대된 발생"을 뜻하고, 달성률·연속 달성·패턴 신호가 전부 그 전제를 재사용한다.

여기에 주기가 없는 루틴을 넣는다. 등록만 해두고 수행한 날에만 기록을 남기는 형태이고, 필요한 분석은 "언제 했는지"와 "이번 달 몇 번" 둘뿐이다. 문제는 그 기록이 같은 테이블에 들어가면서 기존 집계의 분모 정의를 조용히 흔든다는 점이다. 그래서 이 마스터는 기능 추가와 측정 격리를 한 묶음으로 다룬다.

## Phase 1: 추적 모드 이원화 + 측정 격리 (2026-07-26)

- 이슈: [#605](https://github.com/hyewon3938/slack-ai-agents/issues/605)

- 관련 계획서: `.claude/plans/605-routine-tracking-modes.md`
- 상태: 설계 완료

### 결정 요약

루틴 템플릿에 `tracking_mode`(`scheduled` | `free`) 축을 추가하고, 기록에는 `entry_type` 스탬프를 남긴다. 자율 루틴은 자동 생성 없이 수행 시점에만 완료 상태로 INSERT되고, 하루 여러 건을 허용한다. `routine_records`를 "기대된 발생"으로 읽는 모든 소비처(DB 신호 정의 SQL·봇 집계·웹 통계·LLM 프롬프트)에 `entry_type = 'scheduled'` 조건을 넣어 기존 측정의 의미를 고정한다. 웹에는 등록 폼의 모드 선택과 체크리스트 하단 자율 루틴 섹션 + 기록 모달을 만든다.

통계·Slack 기록 경로·신호 시드는 Phase 2로 미뤘다. Phase 1만으로 등록·기록·전환이 동작한다.

### 의사결정 분기점

> "왜 A가 아닌 B를 택했는지"

- **모드를 어디에 표현할까**: (a) `frequency`에 `'자율'` 센티널 값 / (b) 별도 테이블·별도 도메인 신설 / (c) `tracking_mode` 컬럼 + 기록 `entry_type` 스탬프 → **(c) 채택**.
  - (a) 기각: `frequency`는 CHECK 없는 자유 TEXT라 오타를 막을 장치가 없고, 결정적으로 **과거 기록이 어느 시대의 것인지 구분할 수 없다**. 모드를 바꾸면 과거 달성률의 의미가 소급으로 뒤집힌다 — 핵심 원칙 2 위반.
  - (b) 기각: 요구의 무게중심이 "전환"인데, 별도 테이블은 전환할 때마다 정체성을 코드로 봉합해야 한다. 게다가 패턴 검증 엔진의 도메인 매핑(`BEHAVIOR_SIGNAL_DOMAIN`·`DOMAIN_TABLE`)에 새 항목을 추가해야 하고, 히트맵·메모·soft delete처럼 이미 깔린 배관을 전부 다시 깔아야 한다.
  - (c) 채택: 템플릿 행 하나가 모드 전환을 넘어 살아남으므로 정체성이 공짜로 유지된다(원칙 1). 기록은 각자 자기 시대의 성격을 갖는다(원칙 2). 기존 신호 SQL은 조건 한 줄로 고쳐지는데, 대부분의 시드 SQL이 `routine_records` 단독을 보기 때문에 JOIN을 새로 추가할 필요조차 없다.
- **하루 여러 건을 허용할까**: 하루 1건 제한 / 여러 건 허용 → **여러 건 허용**. 하루에 두 번 하는 경우가 실제로 있고 목적이 "이번 달 몇 번"이라, 횟수를 뭉개면 데이터가 목적을 잃는다. 부수 효과로 `entry_type = 'scheduled'` 조건부 유니크 인덱스를 넣으면서 **주기형 쪽의 하루 1건 보장이 처음으로 DB 수준에 생긴다** — 지금까지는 제약이 아예 없었다.
- **기록 진입 경로**: 체크리스트에 그냥 섞기 / 하단 별도 섹션 + 기록 모달 → **후자**. 체크리스트는 "오늘의 의무" 라는 의미를 이미 갖고 있어서, 의무가 아닌 항목을 같은 리스트에 섞으면 그 의미가 흐려진다. 한 단계 더 들어가는 대신 두 성격이 섞이지 않는다.
- **측정 격리를 Phase 1 필수 게이트로 둔 이유**: 어느 설계를 택해도 필요한 작업이기 때문. 기존 운동 루틴을 자율로 옮기는 순간 달성률의 분모 정의가 바뀐다. 미루면 그 사이 오염된 데이터가 확정 게이트(n\~20)를 통과해버릴 수 있어서, 되돌리는 비용이 미룬 이득보다 크다.
- **격리 범위를 어디까지 볼까**: 달성률·연속 달성을 세는 SQL만 / 기록의 존재를 전제하는 곳까지 → **후자**. 탐색 중에 `computeUserDataStarts`가 걸렸다. 도메인별 첫 기록일로 검증·발굴 윈도우를 클립하는 함수(ADR-0044)인데, 과거 날짜로 자율 기록을 남기면 루틴 도메인의 윈도우 시작이 앞당겨지고 그 앞 구간은 데이터가 없는 채로 `0 = fail`로 세진다. 분자도 분모도 건드리지 않는 곳으로도 오염이 샌다는 뜻이라, 후보 목록을 "루틴 기록을 세는 곳"에서 "루틴 기록의 존재를 전제하는 곳"으로 넓혀 다시 훑었다.
- **표시 경로도 SQL로 격리할까**: 전부 SQL에서 자르기 / 집계만 SQL, 표시는 필드로 분기 → **후자**. 집계에서 조건을 빠뜨리면 수치가 조용히 틀리지만, 표시에서 빠뜨리면 화면에 바로 보인다. 게다가 봇의 "활성 루틴 N개" 목록처럼 자율 루틴도 포함해야 정직한 표시가 있어서, 쿼리 단계에서 걸러버리면 오히려 거짓이 된다. 그래서 조회는 성격 필드를 그대로 내려보내고 컴포넌트가 나눈다.
- **기존 중복 점검을 언제 할까**: 마이그레이션 안에서만 / 머지 전 프로덕션 사전 점검 → **둘 다 하되 사전 점검이 게이트**. 마이그레이션은 봇 부팅 시 자동 적용되고 실패를 감싸는 try-catch가 없다. 조건부 유니크 인덱스가 기존 중복 때문에 실패하면 봇이 기동하지 못하고, 적용 이력에 기록도 안 되니 재시작마다 같은 실패를 반복한다. 배포가 곧 적용인 구조에서는 "실패하면 롤백"이 성립하지 않아서, 읽기 전용 중복 확인을 머지 전 필수 게이트로 올렸다.
- **Phase 분할 지점**: 스키마+격리+웹기록 / 통계+Slack+신호 → **2단계**. Phase 1 끝나면 이미 쓸 수 있는 상태다. 반면 통계는 기존 쿼리·타입이 전부 달성률 기반이라 횟수 기반을 새로 만들어야 해서, 분리했을 때 리스크가 가장 낮은 지점이 여기였다.

### 포기한 안 / 미룬 항목

> "Y는 안 했는데 그 이유는"

- **모드 전환 이력 테이블(`routine_mode_periods`)**: 기각. `entry_type` 스탬프가 사실상 이력이다 — 그 날짜 기록의 성격이 그 시기의 모드다. 전환 시점을 분 단위로 알아야 하는 요구가 실제로 생기면 재검토.
- **운동 측정값(`metrics JSONB`)**: 미룸. 트리거 = "이번 달 몇 번"을 넘는 질문이 생기는 시점(거리 추이, 강도 비교 등). 지금 넣으면 스키마는 늘고 입력 UI는 무거워지는데 쓰는 사람이 없다. 원칙 4에 따라 그때는 루틴 확장이 아니라 별도 도메인으로 검토.
- **Slack Modal 기록 폼**: Phase 2로 미루되, 거기서도 모달이 아니라 1클릭 즉시 기록으로 간다. 이 프로젝트는 `views.open`·`trigger_id`를 한 번도 쓴 적이 없어서 모달 도입 자체가 별도 학습·검증 비용이고, 자율 기록은 "했다"만 남기면 되므로 클릭 한 번이 오히려 요구에 맞다.
- **자율 루틴 전용 신호 시드**: Phase 2로 미룸. 데이터가 0인 상태에서 신호를 심으면 휴면 신호만 늘어난다. #477 헌장 ④(후속 미루지 않기 — 데이터 게이트 자동 활성)에 따라, Phase 2에서 휴면으로 심고 데이터 게이트가 스스로 깨우게 한다.

### 미해결·가설

> "이 부분은 자신 없는데 일단 가보는 부분"

- **자율 루틴에서 `start_date`의 의미**: 통계 기산일은 분모가 있을 때 성립하는 개념이라 자율 루틴에서는 무의미하다. 일단 컬럼을 유지하고 UI에서만 숨긴다. Phase 2 통계에서 기준을 `start_date`로 둘지 첫 기록일로 둘지는 미정.
- **모드 전환과 비활성 기간의 상호작용**: 자율 루틴에 비활성 기간은 개념적으로 불필요하다(안 하면 기록이 없을 뿐). UI에서 숨기지만 데이터는 남으므로, 주기형 → 자율 → 주기형으로 돌아오면 예전 비활성 기간이 되살아난다. 이게 맞는 동작인지는 실사용에서 확인.
- **하루 여러 건의 히트맵 표현**: 같은 날 2건을 색 농도로 볼지 숫자로 볼지 미정. Phase 2 과제.

### 기술적 의의

기존 집계의 의미를 건드리지 않고 데이터 모델에 새 축을 추가한 사례. 모드는 정의(템플릿)에, 성격은 사실(기록)에 나눠 저장해 소급 왜곡을 원천 차단했다. 오염 차단은 소비처 23곳을 전수 조사해 범위를 확정하고, 파일별 조건 개수를 완료 조건에 넣어 누락을 검증 가능한 형태로 만들었다.
